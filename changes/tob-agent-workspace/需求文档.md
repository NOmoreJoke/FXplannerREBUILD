# PRD：ToB 组织工作台与 Agent 换汇协作

> 文档状态：待评审，未实施。本文是产品需求与验收依据，不代表现有功能已经具备组织或权限能力。
> 关联文档：技术设计、现状改造与实施计划见 `changes/tob-agent-workspace/技术方案.md`；现有个人 MVP 见 `README.md` 与 `docs/开发计划/MVP开发计划.md`。
> 需求编号：ORG / MEM / AUTH / LEDGER / AGENT / AUDIT / DATA / MIG，供技术方案与测试追踪。

## 1. 背景与问题定义

FXPlanner 当前服务个人换汇计划与成本管理，核心闭环为“建计划 → 分批准备 → 记录买入 → 记录使用 → 更正 → 报告”，AI 助手仅能查询公共汇率。

转向独立站站主、跨境电商及小型贸易公司后，问题不再只是“一个人如何换汇”，而是：

1. 同一公司的负责人、运营和财务需要围绕同一套资金与计划协作。
2. 不同组织的数据必须严格隔离，成员退出或降权后不得继续访问。
3. Agent 需要从“公共汇率问答”升级为“理解本组织资金情况并辅助形成换汇方案”，但不能借模型调用绕过权限。
4. 买入、使用、更正、导出和删除等操作需要知道“谁代表哪个组织做了什么”。
5. 企业账号注销、个人账号注销、组织清空不再是同一语义，不能继续共用纯个人数据模型。

### 1.1 当前产品与 ToB 场景的差距

| 当前能力 | ToB 场景缺口 |
| --- | --- |
| 业务数据直接属于用户 | 没有公司/工作台边界，不能多人共享同一账本 |
| 登录后即是本人全部权限 | 没有成员、角色、降权、移除和所有者转移 |
| Agent 只查公共汇率 | 不能回答本组织余额、计划缺口和成本问题 |
| 更正有个人留痕 | 缺少统一的成员、导出、Agent 和敏感操作审计 |
| 清空、注销按个人账号处理 | 个人退出与公司数据删除混在一起，存在误删风险 |
| 首次设置按用户完成 | 一个用户加入或创建多个组织时无法分别建账 |

### 1.2 产品判断

需要调整领域模型和权限边界，但保留现有个人账本、FIFO 成本、计划、报告与汇率能力。独立站主仍可获得无额外操作的单人默认组织；团队协作按需出现，不把个人用户强制带入复杂企业流程。

## 2. 产品目标与成功标准

### 2.1 产品目标

1. **共享账本**：同一组织内被授权成员看到一致的账户、计划、交易、使用和报告。
2. **最小权限**：成员只执行其角色允许的动作，跨组织访问一律不可见。
3. **可控 Agent**：Agent 能基于当前组织数据回答和起草，但不能突破操作者权限或自主执行真实资金交易。
4. **可追溯**：关键人员、权限、财务变更、数据导出和 Agent 行为可审计。
5. **平滑兼容**：存量个人用户无需重新录入，原有记录自动进入其默认组织。

### 2.2 可判定成功标准

- 存量用户升级后，账户余额、计划分配、交易、使用、更正和报告结果与迁移前一致。
- 一个组织至少可由 Owner 邀请一名成员；被邀请者接受后可按角色访问共享账本。
- 两个组织的相同业务模块之间不存在列表、详情、统计、导出或 Agent 工具数据串联。
- Viewer 的任何直接写请求和 Agent 写请求均被拒绝，而非仅隐藏按钮。
- 成员被移除后，新请求立即失效；进行中的 Agent 流在下一次工具调用时重新鉴权。
- Agent 给出的组织金额、余额、缺口与对应业务页面一致；查不到数据时明确说明，不编造。
- 任一高风险写操作都能从审计记录定位组织、操作者、时间、目标和结果。

### 2.3 非目标

本阶段不做：

- 银行、券商、支付机构的真实换汇、付款或资金划拨。
- 自定义角色、自定义权限点、部门树和复杂 ABAC。
- 多组织合并报表、跨组织资金调拨。
- 按单条计划或账户分配成员可见范围；组织内数据可见范围以角色为准。
- 企业 SSO、SCIM、计费套餐、发票和组织级订阅。
- 独立站/平台订单的实时 API 同步；首阶段不宣称已完成电商回款预测。
- 外币收款后卖出为本位币的完整账本模型。现有买入—支付闭环先服务广告费、供应商款等外币付款场景；收款/卖出方向需另立需求，不能通过给现有 Plan 随意加方向字段冒充支持。
- Agent 自动审批、自动更正或无人值守执行财务写操作。

## 3. 目标用户与核心任务

| 用户 | 典型任务 | 产品对应 |
| --- | --- | --- |
| 独立站站主/个体负责人 | 管理广告费、工具订阅、供应商外币支出；询问汇率与资金缺口 | 默认组织、现有计划闭环、Agent 查询与计划草稿 |
| 跨境电商运营 | 汇总未来付款需求、创建计划、跟踪准备进度 | Operator、共享计划、提醒和 Agent 草稿 |
| 财务/会计 | 核对余额、登记买入和使用、纠错、导出与查看成本 | Finance、财务写权限、报告和审计 |
| 公司负责人/管理员 | 管理团队、控制敏感权限、查看企业整体情况 | Owner/Admin、成员管理、组织设置 |
| 外部顾问/只读管理者 | 查看报告，不修改账本 | Viewer、只读 Agent |

## 4. 版本范围与交付分层

| 版本 | 用户得到什么 | 包含需求 |
| --- | --- | --- |
| R0 个人 MVP 收口前置 | 金额方向与时效可信、USAGE 更正闭环、生产导出可用；冗余请求与 SQL 放大受控 | 现有 MVP 缺陷批次，不属于 ToB 功能交付 |
| R1 组织与权限地基 | 默认组织、组织切换、邀请成员、固定角色、共享账本、审计、个人/组织数据操作分离 | ORG、MEM、AUTH、LEDGER、AUDIT、DATA、MIG |
| R2 组织 Agent | 查询本组织账户/计划/报告；基于当前组织生成计划草稿，人工确认后保存 | AGENT |
| R3 电商业务扩展候选 | 订单/应收/应付导入、收付款方向、店铺/法人和真实业务暴露分析 | 另行 PRD，不在本技术 spec 承诺 |
| R4 真实执行与开放集成候选 | API 凭证、双人审批、真实交易执行 | 另行安全与合规评审，不在本阶段承诺 |

R0 是 R1 组织写迁移的硬前置，R1 是 R2 的硬前置。个人 MVP 的汇率方向、日级报价可用性、USAGE 更正和生产导出未通过回归前，不得启动共享账本写入或邀请成员上线。组织隔离和权限验收未通过前，不得向 Agent 增加任何企业数据读工具。ToB 原型均为后续版本规划，不代表现有 MVP 已具备这些能力。

## 5. 核心概念

| 术语 | 产品定义 |
| --- | --- |
| 组织 Organization | 一套独立企业账本和协作空间；独立站主的个人工作台也是组织 |
| 默认组织 | 存量用户升级或新用户注册时自动创建的个人组织 |
| 当前组织 | 用户本次操作所代表的组织；所有企业业务请求只访问该组织 |
| 成员 Membership | 某用户在某组织中的有效身份；一个用户可属于多个组织 |
| 角色 Role | 一组固定权限：Owner、Admin、Finance、Operator、Viewer |
| 操作者 Actor | 发起动作的人或 API 身份；Agent 始终是代理执行者，不取代操作者 |
| 组织账本 | 当前组织下的账户、计划、交易、使用、分配、更正和报告 |
| Agent 草稿 | Agent 根据数据和用户意图生成、尚未正式保存的建议内容 |
| 审计记录 | 对关键行为的只读事实记录，包含谁、在哪个组织、何时、对什么做了什么 |
| 个人数据请求 | 仅针对账号资料、个人偏好和个人成员关系的导出或注销 |
| 组织数据请求 | 针对某组织账本的数据导出、清空或删除 |

## 6. 组织工作台

### 6.0 登录与组织进入路径（ORG-00）

1. 登录继续验证个人邮箱身份，不新增“企业账号”类型，不让用户在登录时自报组织角色。
2. 登录页说明支持团队协作和组织账本；邮箱、验证码、年龄与条款确认保持现有流程，不展示任何组织余额或业务明细。
3. 登录成功后按服务端有效 Membership 路由：单一组织进入上次有效组织或默认组织；多组织显示组织选择器；无有效组织进入新建组织流程。
4. 带邀请链接进入时先完成登录，再校验登录邮箱、邀请状态和有效期；不能因持有链接绕过身份验证。
5. 组织选择器显示组织名称、当前用户角色和建账状态；切换期间不显示旧组织数据，未建账组织进入其独立首次设置。
6. 成员被移除、禁用或无权访问时显示明确状态，提供返回可用组织、切换组织或退出登录，不保留旧组织敏感内容。

### 6.1 默认组织与新建组织（ORG-01）

1. 存量用户升级时自动拥有一个默认组织，不弹出强制团队设置。
2. 新用户注册后自动创建默认组织，再进入该组织的首次设置。
3. 默认组织名称使用“用户名称/邮箱前缀的工作台”，用户可修改。
4. 已登录用户可以新建组织；新组织必须有独立本位币、记账起点和账本。
5. 新组织创建者是 Owner，创建组织不复制其他组织的业务数据或成员。

### 6.2 组织切换（ORG-02）

1. 顶栏显示当前组织名称；属于多个组织时可打开切换器。
2. 切换后，首页、账户、计划、交易、使用、更正、报告、提醒、设置和 Agent 均只显示新组织内容。
3. 不属于当前用户的组织不能通过手改地址、请求参数或缓存被选中。
4. 切换组织时取消旧组织正在进行的查询和表单提交；旧组织未保存表单不得自动带入新组织。
5. 当前组织选择可记住到下次登录，但记住的只是选择，不构成访问凭证。
6. 单组织用户不显示复杂切换界面，只显示组织名称和设置入口。

### 6.3 组织生命周期（ORG-03）

1. 组织状态至少有正常、清空/删除处理中两种可用性表现。
2. 组织删除仅 Owner 可发起，必须完成高危二次验证并阅读不可恢复提示。
3. 最后一个 Owner 不能直接退出、被移除或被降权；必须先转移所有权。
4. 组织删除不影响成员的个人账号及其他组织。

## 7. 成员与角色

### 7.1 邀请成员（MEM-01）

1. Owner、Admin 可通过邮箱邀请成员，并指定 Admin、Finance、Operator 或 Viewer；Admin 不能邀请或提升为 Owner。
2. 邀请显示组织名、邀请人、角色和有效期；默认有效期 7 天。
3. 接受邀请前用户须登录，且登录邮箱与受邀邮箱一致。
4. 邀请链接只能使用一次；过期、撤销或已接受后不可再次使用。
5. 重复邀请同一邮箱时返回现有有效邀请，不产生多封相互冲突的有效邀请。
6. 被邀请者可以接受或拒绝；拒绝不自动加入组织。
7. 邀请邮件不包含账户余额、交易明细或任何组织业务数据。

### 7.2 角色调整与移除（MEM-02）

1. Owner 可调整任意成员角色；Admin 可管理 Finance、Operator、Viewer，不可管理 Owner。
2. Owner 转移采用显式动作：当前 Owner 指定一名有效成员成为新 Owner，原 Owner 默认变为 Admin。
3. Owner、Admin 可移除其可管理范围内的成员；移除后该成员立即失去组织访问权。
4. 移除成员不删除其历史操作记录；历史中的操作者信息保留为可审计快照。
5. 成员可以主动退出组织，但最后 Owner 必须先转移所有权或删除组织。
6. 被移除成员的个人账号、其他组织和个人会话不受影响。

### 7.3 固定角色权限（AUTH-01）

| 能力 | Owner | Admin | Finance | Operator | Viewer |
| --- | --- | --- | --- | --- | --- |
| 查看组织账户、计划、交易、使用、报告 | ✓ | ✓ | ✓ | ✓ | ✓ |
| 查看组织审计记录 | ✓ | ✓ | ✓ | — | — |
| 修改组织名称与业务偏好 | ✓ | ✓ | — | — | — |
| 邀请/移除成员、调整普通角色 | ✓ | ✓，限普通角色 | — | — | — |
| 转移所有权、删除组织 | ✓ | — | — | — | — |
| 创建计划、调整计划、导入草稿 | ✓ | ✓ | ✓ | ✓ | — |
| 记录买入与使用 | ✓ | ✓ | ✓ | — | — |
| 发起并完成更正 | ✓ | ✓ | ✓ | — | — |
| 组织数据导出 | ✓ | ✓ | ✓，需二次验证 | — | — |
| 组织清空 | ✓ | ✓，需二次验证 | — | — | — |
| 使用公共汇率 Agent | ✓ | ✓ | ✓ | ✓ | ✓ |
| 使用组织数据 Agent | ✓ | ✓ | ✓ | ✓ | ✓，只读 |
| 保存 Agent 生成的计划草稿 | ✓ | ✓ | ✓ | ✓ | — |

补充规则：

- 表中“—”表示服务端拒绝，不只是前端不展示。
- Finance 可以创建和调整计划，但不管理成员或组织设置。
- Operator 不记录买入、使用和更正；如需这些能力，应调整为 Finance。
- 组织数据导出继续要求二次验证，角色通过不等于跳过安全确认。
- Agent 权限取当前操作者与工具所需权限的交集，没有独立超级权限。

### 7.4 权限变化生效（AUTH-02）

1. 每次组织业务请求均验证当前成员状态和最新角色。
2. 降权、移除和所有权转移不依赖旧 JWT 过期才生效。
3. 前端收到权限变化结果后刷新组织上下文；无权页面显示无权限或返回组织首页，不展示旧缓存数据。
4. Agent 每次调用组织工具前重新使用最新成员身份鉴权，防止流式会话期间降权继续取数。

## 8. 共享组织账本

### 8.1 数据共享与归属（LEDGER-01）

1. 账户、初始持仓、交易、计划、分配、使用、更正和报告属于组织，不再属于某个创建成员。
2. 创建者只用于审计，不决定其他成员能否读取组织数据。
3. 同一组织的授权成员看到相同余额、计划分配、FIFO 成本和报告结果。
4. 记录列表可增加“记录人/最后修改人”，但这不是权限筛选条件。
5. 跨组织访问记录时按“不存在”处理，不泄露记录是否存在。

### 8.2 组织设置与首次设置（LEDGER-02）

1. 本位币、记账起点、默认准备节奏和提醒开关属于组织。
2. 语言、地区展示偏好属于个人；后续若需组织默认语言，再单独设计。
3. 用户新建组织后需完成该组织首次设置；一个组织已建账不代表其他组织也已建账。
4. 本位币锁定、清空后重置记账起点等既有规则保留，但作用于当前组织。
5. 未建账组织不发送业务提醒，不产生重复的设置/提醒失败请求。

### 8.3 提醒与已读（LEDGER-03）

1. 计划到期和准备事项属于组织。
2. 提醒已读状态按成员分别记录；一名成员已读不能替其他成员清除其未读。
3. 只有拥有对应业务查看权限的成员接收该组织提醒。
4. 成员被移除后不再生成或展示该组织提醒。

### 8.4 并发与更正（LEDGER-04）

1. 保留现有乐观版本、影响预览和事务重放规则。
2. 预览后若其他成员修改了同一记录，提交者必须看到最新影响并重新确认。
3. 使用记录更正必须在组织模型下补齐，不得只支持个人旧入口。
4. 更正日志除原有前后快照外，还必须显示实际操作者和所属组织。

## 9. Agent 产品需求

### 9.1 会话边界（AGENT-01）

1. 会话仍属于创建用户，同时绑定创建时的组织；不默认成为全组织共享会话。
2. 会话列表默认只显示当前用户在当前组织的会话。
3. 用户切换到其他组织后，不自动看到原组织会话，也不能通过旧会话继续查询原组织。
4. 用户被移除组织后，无法继续访问绑定该组织的会话。
5. 公共汇率会话与组织会话可使用同一界面，但组织工具是否可用由当前上下文决定。

### 9.2 R2 组织只读工具（AGENT-02）

Agent 至少支持以下问题：

- “我目前各币种余额和未分配余额是多少？”
- “未来 30 天有哪些计划需要准备，缺口分别是多少？”
- “这个计划已经用了多少，FIFO 成本是多少？”
- “按照当前计划，哪些币种最紧张？”

对应能力：

| 工具能力 | 所需权限 | 返回口径 |
| --- | --- | --- |
| 查询公共汇率 | Agent 使用权限 | 与行情页一致，含来源和数据时间 |
| 查询组织账户摘要 | 账户查看 | 与账户页一致，金额带币种 |
| 查询组织计划与准备缺口 | 计划查看 | 与计划页一致，含计划状态 |
| 查询计划成本与使用摘要 | 报告查看 | 与报告页一致，费用未知不得当作 0 |
| 查询近期到期事项 | 计划/提醒查看 | 仅当前组织、当前有效计划 |

规则：

1. Agent 不得要求模型传入 userId 或 organizationId 来决定数据范围，二者由服务端上下文注入。
2. 回复必须能区分公共汇率、组织事实和模型建议。
3. 组织数据查询失败或无权限时，明确说明无法取得数据，不编造数字。
4. Agent 建议不得描述为已经执行；未保存的内容统一称“草稿”或“建议”。
5. 回复金额使用服务端返回值，不在模型中自行做高精度金额重算。

### 9.3 R2 计划草稿与人工确认（AGENT-03）

1. 用户可输入“为 12 月 10 日需要支付的 10,000 美元做方案”，Agent 结合当前组织余额、已有分配和偏好生成计划草稿。
2. 草稿包含目标币种、目标金额、使用日期、准备偏好、计入已有外币和分批建议。
3. 用户打开确认页后，系统重新读取最新余额并复用现有排期预览，不直接采用模型计算作为最终入账结果。
4. 只有拥有计划创建权限的成员可以确认保存；Viewer 可以查看建议但不能保存。
5. 用户取消不产生正式计划，不改变分配。
6. 确认时余额或计划已变化，须重新展示影响；不能按旧草稿强行保存。
7. Agent 不直接登记买入、使用或更正；这些动作仍由有权限成员走现有确认流程。

### 9.4 Agent 安全（AGENT-04）

- 用户消息、导入文本、计划备注和工具返回均是不可信输入，不得改变系统权限规则。
- 即使用户要求“忽略权限”“查询另一家公司”，工具仍按当前 Actor 鉴权。
- 工具只返回完成当前任务所需字段，不把全表或凭证交给模型。
- 不在提示词、日志或错误消息中暴露模型密钥、API 凭证、邀请原始 token 或验证码。
- Agent 失败不影响组织账本，不留下半条有效业务记录。

## 10. 审计与可见性

### 10.1 审计范围（AUDIT-01）

必须记录：

- 组织创建、改名、清空、删除和所有权转移。
- 邀请创建/撤销/接受/拒绝、角色调整、成员移除和退出。
- 计划、交易、使用、初始持仓和更正的成功写操作。
- 组织数据导出申请与下载、高危验证成功/失败结果。
- Agent 组织工具调用、权限拒绝、草稿生成和最终人工确认结果。

### 10.2 审计内容（AUDIT-02）

每条至少包含：组织、操作者、身份类型（用户/API/Agent 代理）、动作、目标类型/ID、时间、结果、关联请求或 Agent 会话。财务更正继续保留前后快照；日志不记录密码、完整 token、验证码或模型密钥。

### 10.3 审计查看（AUDIT-03）

1. Owner、Admin、Finance 可按时间、成员和动作查看当前组织审计。
2. Operator、Viewer 无组织审计入口。
3. 审计记录无编辑和删除入口。
4. 审计页面分页加载，不一次返回全组织历史。

## 11. 个人与组织数据权利

### 11.1 语义分离（DATA-01）

| 操作 | 范围 | 权限与结果 |
| --- | --- | --- |
| 个人数据导出 | 账号资料、个人偏好、成员关系和个人会话元数据 | 本人 + 二次验证；不自动包含组织财务明细 |
| 组织数据导出 | 当前组织账本和报告 | Owner/Admin/Finance + 二次验证 |
| 组织清空 | 当前组织业务账本 | Owner/Admin + 二次验证；其他组织不受影响 |
| 组织删除 | 当前组织及其业务数据 | Owner + 二次验证；成员个人账号保留 |
| 个人账号注销 | 个人账号和剩余个人数据 | 本人 + 二次验证；须先处理最后 Owner 组织 |

### 11.2 锁定规则（DATA-02）

1. 个人注销只锁个人身份，不锁其曾参与的其他组织账本。
2. 组织清空/删除按当前组织锁定，不影响同一用户或其他成员访问其他组织。
3. 组织锁期间，组织进度页和白名单端点按现有原则可用。
4. 个人是某组织最后 Owner 时，不能直接注销并遗留无主组织；必须先转移所有权或完成组织删除。
5. 组织导出下载者必须仍具备组织导出权限；成员被移除后原下载链接不可继续使用。

## 12. 存量用户迁移体验（MIG-01）

1. 升级后原用户自动成为其默认组织 Owner。
2. 原账户、交易、计划、使用、更正、设置、提醒和 AI 会话归属到该默认组织。
3. 原记录的业务时间和计算结果不变；创建者标记为原用户。
4. 用户无需重新完成首次设置，原组织本位币和记账起点保持不变。
5. 首次进入可显示一次简短说明：“你的个人账本已升级为可邀请成员协作的工作台”，不强制邀请。
6. 迁移失败不得表现为空账本或部分成功；必须保留可恢复路径和核对记录。

## 13. 页面与交互要求

| 页面/区域 | 新增或调整 |
| --- | --- |
| 登录/注册 | 保留个人邮箱 OTP；使用团队协作定位，不采集角色，不展示组织业务数据 |
| 登录后路由/组织选择 | 单组织直达、多组织选择、无组织创建；显示角色与建账状态 |
| 保护区顶栏 | 当前组织名称、组织切换器、权限感知的操作入口 |
| 组织设置 | 基本信息、本位币/记账信息、成员与邀请、审计、组织数据操作 |
| 首次设置 | 明确正在为哪个组织建账；不同组织分别完成 |
| 账户/计划/交易/使用/更正/报告 | 显示共享组织数据；操作按钮按权限显示，后端仍强制校验 |
| 提醒 | 当前组织事项；个人已读；无组织/未建账时不发无效请求 |
| AI 助手 | 显示当前组织；区分事实、建议和草稿；组织工具状态可见 |
| 邀请接受页 | 展示组织、角色、邀请人、有效期和接受/拒绝 |
| 无权限/成员失效 | 明确提示并清理旧组织缓存，不显示空白或陈旧敏感数据 |

可访问性底线：组织切换、邀请、角色修改、确认弹窗和 Agent 草稿均可用键盘完成；危险操作不能只用颜色表达。

## 14. 非功能需求

### 14.1 安全与隐私

- 所有组织业务端点、导出下载和 Agent 工具都必须服务端鉴权。
- 跨组织资源统一按不存在处理，避免 ID 枚举。
- 成员状态和角色以服务端最新记录为准。
- 高风险操作保留二次验证；权限系统不能替代验证机制。
- 日志和错误上报不包含完整财务快照、凭证或邀请 token。

### 14.2 一致性与性能

- 业务写操作和审计在同一数据库事务中成功或失败。
- 组织切换不得短暂展示上一组织数据；缓存键必须包含组织。
- 迁移前后金额和 FIFO 结果必须逐组织一致。
- 常规组织业务接口在现有个人 MVP 参考数据量下不因权限检查出现明显不可用；具体基准和 SQL 验证由技术 spec 规定。
- Agent 沿用流式与中止机制，组织工具不能阻塞其他业务写事务。

### 14.3 可观测性

至少可观察：组织切换失败、权限拒绝、邀请状态、迁移回填数量、跨组织访问拦截、Agent 工具权限失败、组织数据请求状态和审计写入失败。不得把这些事件只留在浏览器控制台。

## 15. 验收标准（Given-When-Then）

### 15.1 组织与迁移

1. **默认组织**：假如一个存量用户已有完整账本，当升级后首次登录，那么其成为默认组织 Owner，所有原记录和报告可见且金额不变。
2. **新建隔离**：假如用户已有组织 A，当创建组织 B，那么 B 没有 A 的账户和计划，且需要单独完成首次设置。
3. **切换一致性**：假如用户同时属于 A、B，当从 A 切换到 B，那么首页、账户、计划、报告和 Agent 均只显示 B 数据。
4. **无缓存串数据**：假如 A 页面已经加载，当快速切换到 B，那么 A 的迟到响应不会覆盖 B 页面。
5. **最后 Owner**：假如组织只有一名 Owner，当其尝试退出或被降权，那么操作被拒绝并提示先转移所有权。

### 15.2 成员与权限

6. **邀请全流程**：假如 Owner 邀请一名 Finance，当受邀者使用匹配邮箱登录并接受，那么其成为有效成员并看到共享账本。
7. **错误邮箱**：假如邀请发给邮箱 A，当邮箱 B 的用户尝试接受，那么被拒绝且不产生成员关系。
8. **邀请失效**：假如邀请已过期、撤销或接受，当再次使用链接，那么提示无效，不新增成员。
9. **Operator 边界**：假如 Operator 创建计划成功，当其尝试记录买入或更正，那么服务端拒绝且账本不变。
10. **Viewer 边界**：假如 Viewer 隐藏界面后直接构造写请求，当请求到达服务端，那么被拒绝，且审计记录该次敏感拒绝。
11. **跨组织隔离**：假如成员只属 A，当其用 B 的记录 ID 请求详情、修改、导出或 Agent 查询，那么无法得到 B 的任何内容。
12. **即时降权**：假如 Finance 被降为 Viewer，当其使用旧页面发起交易，那么按 Viewer 拒绝，不等待旧 JWT 过期。
13. **成员移除**：假如成员被移除，当其刷新或使用进行中的旧 Agent 会话再次调用组织工具，那么访问失败。
14. **所有权转移**：假如 Owner 将所有权转给 Admin，当操作完成，那么新 Owner 可管理组织，原 Owner 变为 Admin，审计包含双方与组织。

### 15.3 共享账本

15. **共享一致性**：假如 Finance 新增买入，当 Operator 刷新账户和计划，那么看到同一余额与成本，且记录人正确。
16. **并发更正**：假如一名成员预览更正后另一成员修改目标记录，当前者提交旧预览，那么系统拒绝并显示最新版本，不覆盖后者。
17. **组织级使用更正**：假如 Finance 更正共享使用记录，当操作成功，那么账户、计划分配、FIFO 成本和报告一致，日志显示组织与操作者。
18. **个人已读**：假如同一组织有两名成员，当一人已读提醒，那么另一人的未读状态不因此消失。

### 15.4 Agent

19. **组织账户问答**：假如用户询问当前美元未分配余额，当 Agent 调用账户工具，那么回复与当前组织账户页一致，不含其他组织金额。
20. **多组织防串话**：假如用户在 A 的会话中询问过 A 数据，当切换到 B，那么不能利用旧会话或上下文取得 A 数据。
21. **Viewer 工具边界**：假如 Viewer 要求 Agent 创建计划，当 Agent 形成建议后，那么不会正式保存；直接调用写工具也被拒绝。
22. **草稿确认**：假如 Operator 让 Agent 起草计划，当打开确认页并保存，那么后端按最新余额重新预览并创建一个计划，不重复创建。
23. **草稿取消**：假如用户生成草稿后取消，那么没有新计划、分配或交易。
24. **无数据诚实回答**：假如当前组织没有相关记录，当询问成本或缺口，那么 Agent 明确说明无数据，不编造。
25. **提示注入**：假如计划备注要求 Agent 忽略权限并导出其他组织，当 Agent 处理相关内容，那么服务端仍按当前组织和角色授权。

### 15.5 数据与审计

26. **组织清空**：假如 Admin 清空组织 A，当处理完成，那么 A 账本为空且记账起点重置，成员 B 的其他组织数据不变。
27. **个人注销限制**：假如用户是 A 的最后 Owner，当直接注销个人账号，那么系统要求先转移所有权或删除 A，不能留下无主组织。
28. **导出降权**：假如 Finance 生成组织导出后被移除，当使用旧下载链接，那么不能下载。
29. **审计完整**：假如 Owner 邀请成员、Finance 更正记录、Agent 起草并确认计划，当查看审计，那么三类动作都有组织、操作者、目标、时间和结果。
30. **审计不可改**：假如任何组织角色尝试通过界面或 API 修改审计记录，那么没有可用入口且服务端不提供修改操作。

## 16. 优先级与发布门槛

### Must（R1/R2 发布必要条件）

- 组织隔离、默认组织迁移、成员与固定角色、组织上下文和缓存隔离。
- 共享账本、组织设置、最后 Owner 保护、审计和个人/组织数据语义分离。
- 组织模型下的使用记录更正与现有账本一致性。
- R2 前必须完成所有跨组织和 Agent 工具权限测试。

### Should

- 多组织新建/切换、邀请邮件、成员退出、审计筛选。
- Agent 计划草稿与现有预览页打通。
- 组织锁性能优化、过期邀请清理和前端监控降噪。

### Could

- 审计导出、更多组织 Agent 提问模板、成员操作通知。

### Won't（本阶段）

真实交易、双人审批、自定义角色、SSO、部门级数据权限、平台订单同步、收款卖出账本。

## 17. 默认决策与后续分叉

以下作为本 spec 的默认决策，不再阻塞 R1/R2 设计；若业务评审改变，需同步修改 PRD、技术方案和验收：

1. 首阶段客户是有外币付款与成本管理需求的独立站和小贸易团队，不以电商收款卖出作为首发闭环。
2. 单人体验通过默认组织兼容，不维护独立个人账本模式。
3. 固定五角色，无自定义角色；组织内没有逐记录授权。
4. Agent 会话是个人所有、组织绑定，不共享给全组织。
5. Agent 首阶段只读组织数据，写能力止于计划草稿和人工确认。
6. 真实换汇执行不在本阶段，不提前建设支付审批或交易连接器。
7. 个人数据权利与组织数据权利分离，个人注销不得自动删除最后 Owner 的组织。
8. 数据保留期限和法定留存清单如需调整，必须经过独立法务/合规评审，本 PRD 不作法律承诺。
