# 汇率定时刷新规格说明书（SRS）

> 状态：已拍板（2026-09-16 讨论），技术方案已过审并实施完成（2026-09-20，验收证据见技术方案 §6.3）。
> 决策记录：现在就加定时任务；频率 = 每整点、每半点各一次；存储 = Postgres 落库（明确排除 Redis）。

## 一、引言

### 1.1 编写目的与读者

对齐「汇率定时刷新」功能的业务目标与验收边界；读者为开发者与验收者。

### 1.2 项目背景

FXPlanner 的录入与报告依赖汇率数据。当前汇率完全按用户请求按需拉取（5 分钟窗口缓存）：没人查询就永不落库，导致 TWD 等无历史能力币种的历史数据始终为空；未来报告/历史模拟批量取数也只能逐笔回源外部接口。

### 1.3 术语与缩写

- **牌价/报价**：外部汇率源返回的某时点汇率
- **积累起点**：本系统数据库中某币种最早一条报价的日期
- **回源**：缓存不可用时向外部汇率源发起请求

## 二、总体描述

### 2.1 系统目标

让系统"自己持续攒汇率数据"：无论有没有用户查询，报价都按固定节奏进入本地库，使历史查询、报告取数不依赖外部源的实时可用性。

### 2.2 用户角色

| 角色 | 能做什么 |
|---|---|
| 所有用户（无感知） | 查询最新/历史汇率时，享受更完整的本地数据；无需任何操作 |

### 2.3 边界（明确不做什么）

- 不改变现有按需拉取逻辑（用户请求仍可触发回源，两者共存）
- 不引入 Redis 等新存储（Postgres 落库足够）
- 不保证外部源故障时的数据补齐（错过的时点就是没有，历史查询如实反映）
- 本期仅刷新默认本位币 CNY 视角的报价；用户自选其他本位币时仍走按需拉取兜底

## 三、功能需求

### 模块1：定时刷新能力

1. **能力简述**：系统每整点、每半点自动拉取一次 15 币种（CNY 视角）最新报价并落库
2. **业务流程**：定时点到达 → 系统按既有路由拉取（农行主源 / frankfurter 补 MYR / er-api 补 TWD）→ 成功报价写入本地库 → 失败的币种不影响其他币种
3. **核心场景与验收路径**（系统行为型）：

   > `当 整点/半点到达 → 预期：系统自动完成一轮拉取落库，无需任何用户触发；此后任意用户查询 TWD 历史，能看到从功能上线日起持续积累的数据`

   > `当 某外部源本轮失败 → 预期：该源币种本轮无新数据，其余源币种正常落库；系统不崩溃、下一轮继续`

   > `当 外部源返回与上轮相同的牌价 → 预期：本地库仅更新不新增冗余记录`

4. **状态规则**：定时任务失败不告警打扰用户（与现有按需拉取的错误语义一致），由日志可查

### 模块2：历史数据可见性（受益方，本期不改动）

1. **能力简述**：现有历史查询能力不变，但 TWD 历史从"空"变为"自上线日起可持续积累"
2. **验收路径**：

   > `当 定时功能运行 ≥1 天后，用户查询 TWD 对 CNY 历史 → 预期：能看到上线以来按牌价时点积累的数据，而非空结果`

## 四、验收清单

- [x] 定时任务按整点/半点触发，一轮覆盖 15 币种（CNY 视角）——单测 SchedulerRegistry 断言 `0 */30 * * * *` + 接口测试 succeeded 15 币种
- [x] 单源失败不影响其他源；任务异常不中断后续轮次——接口测试 abc 500 → 12 failed / TWD+MYR+CNY 照常；单测“异常后下一轮继续”
- [x] 重复牌价不产生冗余存储——接口测试同牌价两轮后行数不变（upsert 幂等）
