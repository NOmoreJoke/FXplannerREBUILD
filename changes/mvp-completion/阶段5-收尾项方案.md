## 1. 首页正常态"新建计划"直达入口

### 需求描述

规格 03 将「新建计划」列为首页功能之一：用户可以从首页直接创建换汇计划。现状只有空状态首页（`HomeEmptyState`）提供入口；已建账用户看到的正常态首页顶栏仅有「录入买入」，创建计划必须先绕行导航或计划列表页，与规格不符，也弱化了产品的核心动作。

### 技术设计

在正常态首页顶栏操作区追加「新建计划」次级入口，与「录入买入」并排（快速录入仍为主按钮，新建计划用 outline 次按钮，主次分明）。空状态分支不动（已有自己的引导入口，且与正常态互斥渲染）。

涉及文件与改动点：

- `clients/chat-web/components/business/home/home-dashboard.tsx`（M）：顶栏 `<header>` 操作区（现仅「录入买入」Link 处）追加一个 `Link href="/plans/new"`，复用 `buttonVariants({ variant: "outline" })` + lucide `Plus` 图标。

无后端改动，无新组件（顶栏两行内联 Link 即可，不满足进 `components/base/` 的复用门槛）。

### 测试要点

- E2E：正常态首页可见「新建计划」入口且 `href` 为 `/plans/new`，点击后落至计划创建页（并入 §5 之 `07-plan-lifecycle.spec.ts` 首步或 `06-navigation.spec.ts` 扩断言）。
- 手动走查：空状态分支不出现重复入口（互斥分支，代码走查即可）。

## 2. 账户页"按计划分配视图"（功能 13 收尾）

### 需求描述

规格 04「把外币分给计划」明确规定：**账户页只展示各计划分配金额和未分配余额，分配和调整在计划中操作**。即本视图是纯只读的事实展示，不得提供任何分配/调整操作（spec 硬约束，前端不放按钮、后端不出写接口）。

现状缺口：账户详情接口已返回 `allocatedAmount` / `unallocatedAmount` 的**币种级汇总**，但无**按计划逐条明细**，用户在账户页看不到"钱分给了哪些计划、各占多少"。功能 13 因此停留在 🟡。

### 技术设计

后端新增 1 个只读端点，前端账户详情页增加 1 个只读表格区块。

**接口契约**（新增，唯一写进契约的增量）：

| 项 | 内容 |
| ---- | ------ |
| 路径 | `GET /api/accounts/:currencyCode/allocations` |
| 出参 | `data: { items: AccountPlanAllocationDto[] }`，按计划创建时间升序（稳定确定） |
| 鉴权/错误 | `JwtAuthGuard` 显式挂载（controller 先例）；400 `INVALID_ACCOUNT_CURRENCY` / 404 `ACCOUNT_NOT_FOUND` 复用详情接口口径，不泄露存在性 |

`AccountPlanAllocationDto`：

```json
{
  "planId": "cmd…",
  "planName": "学费计划 | null",
  "planStatus": "ACTIVE | COMPLETED | CANCELLED",
  "amount": "6000.0000",
  "usedAmount": "4000.0000",
  "remainingAllocation": "2000.0000"
}
```

口径约定：

- **不过滤计划状态**，与 `allocatedAmount` 汇总口径完全一致（`account-calculator.ts` §3.3：全部计划，CANCELLED 已释放计剩余 0 仍如实列出）；`remainingAllocation = amount − usedAmount`（Decimal，服务端算好）。
- PlanAllocation 与 Plan 为裸外键无 relation，沿用内存 join 先例（`services/chat/src/account/account.service.ts:72`）；序列化 `toFixed(4)` 只在 DTO 层做。
- 无分页（个位到十位级，limit 100 兜底对齐 plan 列表约定）。

**前端**：账户详情页在摘要卡与流水之间插入「计划分配」区块，新组件为纯只读表格（计划名 + 状态徽标 / 分配总额 / 累计已使用 / 剩余分配），底部合计行展示**未分配余额**（直接取 `AccountDetailDto.unallocatedAmount`，禁止前端重算）。空态文案「暂无计划分配该币种」。

涉及文件与改动点：

- `services/chat/src/account/dto/account.dto.ts`（M）：新增 `AccountPlanAllocationDto`、`AccountPlanAllocationListDto`。
- `services/chat/src/account/account.service.ts`（M）：新增 `allocations(userId, currencyCode)`：并行查账户（复用 `detail` 的校验路径）+ `planAllocation.findMany` + 内存 join `plan`，逐条计算剩余分配。
- `services/chat/src/account/account.controller.ts`（M）：新增 `@Get(":currencyCode/allocations")`，套 `withLog`，注册 `ApiExtraModels`。
- `clients/chat-web/lib/api/accounts.ts`（M）：新增 `allocations()` API 封装；类型走 `bun run generate:api` 生成，禁止手写（AGENTS.md）。
- `clients/chat-web/components/business/account/plan-allocation-table.tsx`（A）：只读表格组件（含空态），更新 `index.ts` 桶文件。
- `clients/chat-web/app/(protected)/accounts/[currency]/page.tsx`（M）：第三个并行 `useQuery` + 渲染区块，沿用现有 loading/error/404 分支。

### 测试要点

- 接口测试：追加进 `services/chat/test/api/account.spec.ts`（一个 controller 一个文件）——多计划分配的逐条金额与剩余分配；已取消计划剩余 0 如实返回；无分配账户返回空数组；404/400 与详情接口一致；他人账户 404。
- 单测：`account-calculator.spec.ts` 追加剩余分配派生口径（如逻辑落 calculator 层；仅编排则免）。
- E2E：并入 §5 之 `02-account` 扩展或 `07-plan-lifecycle`（建计划→分配→账户详情页可见该计划行与未分配余额；取消计划后剩余归 0、未分配余额恢复）。

## 3. 计划列表进度条

### 需求描述

规格 03 要求首页/计划摘要可「分别查看资金准备情况和实际使用情况」。现状计划列表卡（`plan-list.tsx`）只有金额四项与日期，无任何进度展示，用户需逐个点进详情才能比较各计划准备程度。

### 技术设计

列表卡金额区下方追加一行 `Progress`（`components/ui/progress` 已有，shadcn 原语不手改）+ 百分比文本。

**口径**（与 M7 方案 §3.4 对齐，避免两处进度各说各话）：

- 准备进度 =（目标 − 缺口）÷ 目标 × 100。`gap` 由服务端 `plan-calculator` 唯一计算并已在 `PlanListItem` 下发，前端只做一次展示除法——符合"派生量口径服务端唯一"约定。
- 展示层换算用 Decimal 字符串运算，禁止裸 `parseFloat` 算钱（先例 `clients/chat-web/lib/hooks/use-home-state.ts:92`：四舍五入取整、钳位 0-100、targetAmount=0 → 0）。
- 说明：首页焦点计划横幅的「分配进度」（allocated ÷ target）是另一既有口径，本项不改动它；M7 落地时如需统一，在 M7 变更内处理。

所有计划状态均按同一公式如实展示（已完成/已取消按其冻结数据计算），不做特判。

涉及文件与改动点：

- `clients/chat-web/components/business/plan/plan-list.tsx`（M）：`PlanCard` 内新增进度行（派生函数内联，组件级展示逻辑不外提）。

无后端改动。

### 测试要点

- E2E：`03-plan.spec.ts` T-PLAN-002 扩断言——列表卡渲染进度条且百分比与该计划目标/缺口一致（走查 0%、50%、100% 三档种子数据）。
- 前端组件不写组件测试（项目约定：前端只测 `lib/hooks`，组件验证靠 E2E）；派生逻辑保持内联，若未来第二处复用再抽 `lib/` 并补单测。

## 6. 功能 29"修改计划日期"：建议移出 MVP

### 需求描述（结论）

**建议：不做，明确移出 MVP，作为待确认项记录。**

### 理由

1. **规格未收敛，实现即自造规则**：规格 06「日期怎样计算」明确"哪些日期可以修改、计划在什么状态下可改、怎样影响旧安排"均为待确定；在规则空白时实现，产品行为将由代码拍板而非需求确认。
2. **影响面广且与未开工模块耦合**：日期驱动准备节点（installments）重排，并直接决定 M9 提醒触发与 M10 报告比较口径；仓促实现大概率在阶段 4 模块落地后返工。
3. **上游依赖本身待定**：工作日/节假日日历未确定（06 待确定项），修改日期会放大该不确定性。
4. **用户已有低损兜底路径**：填错日期可取消计划重建——分配自动释放、交易与账户余额不变、`PlanChangeLog` 保留全部历史，资金零损失。属低频、可恢复场景，不值得为它承担上述 1-3 的风险。

### 处置记录

- 在 `docs/MVP功能模块&业务逻辑&专业术语/06_创建换汇计划.md` 待确定清单中已有记录，无需改文档；本项在审查报告中标记为「移出 MVP，待规格收敛后另行立项」。
- **无需 schema/接口预留**：现有 `expectUseDate` / `latestPrepDate` / `pacePreference` / `prepLeadDays` 字段已完整覆盖未来实现所需数据，将来重启该功能是纯增量，不存在"现在不留接口以后补不上"的问题。
- 重启条件：工作日日历与提醒规格（08_提醒与到期处理）收敛，且修改规则（可改字段、适用状态、旧安排处理）经需求确认。
