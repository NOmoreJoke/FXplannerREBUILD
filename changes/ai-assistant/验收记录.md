## 3. 已知问题（E2E 追问链路时序簇，转 P1）

**现象**：E2E 全套（57/63 通过）中 T-AI-003/004/006 确定性失败（单跑、连跑均复现，非 flaky）。

**排查证据链（2026-11-03）**：

1. **后端清白**：curl 直连「新建→追问」全链路 3.5s 完整 done 帧并落库；接口测试 27/27。
2. **前端在干净时序下正常**：独立浏览器复现（Enter 发送、不打断流）下，追问完整渲染并落库（DB 验证 user,user,assistant）。
3. **根因簇**（多层叠加）：
   - **T-AI-002 不断言流完成**：首条流需 ~4.5s（45 帧×80ms），002 的断言 ~2s 即全过、测试返回；后续用例 `openChat` 的 `page.goto` 导航会 abort 尚在进行的流（服务端日志 `AI 流失败（stage=llm）：This operation was aborted`），助手消息不落库 → 003 恢复断言拿不到 assistant。
   - **中断流的状态残留**：流被导航打断后，前端对 abort 静默（isAbortError 不置错误态）；复现中观察到 reload 打断流后，后续 send 被流状态守卫（selectAnyStreaming）静默拦截的现象——指向中断后的流态清理缺陷（chat-store 运行时态不落盘的约定在某路径下未闭环）。
   - **级联放大**：003 失败触发 Playwright 重试 → worker 重启 → `beforeAll` 的 seed 用户被替换 → 004/006 依赖的跨用例会话（「你好」）不存在 → 连锁失败（DB 中观察到同一文件多用户秒级创建）。
   - 8:14 轮（restore 成功、追问 POST 200）中追问流仍在 ~1s 内被打断——该子场景未在干净复现中重现，疑与同一簇相关，随专项修复一并验证。

**修复建议（P1 立项 `ai-chat-e2e-hardening`）**：
- 测试侧：002 补「完整回复 + 停流」断言（对齐 T-AI-003 的前置）；评估 seed 造数改为 per-test 或显式等待流结束。
- 产品侧：中断流应向用户呈现可感知状态（静默吞掉 abort 违反「错误信息纪律」）；核查中断后 streamingIds/creatingStream 清理（send 守卫卡死）。
- 环境（已于本日修复）：turbo.json `dev.env` 补齐 AI_PROVIDER_* 白名单变量（旧名 `AI_LLM_API_KEY` 已死，E2E 密钥被 strict 模式剥离导致 503 假失败）。
