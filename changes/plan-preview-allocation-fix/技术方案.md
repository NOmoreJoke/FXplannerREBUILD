# 排期预览接入「计入已有外币」扣减（FXP 缺陷修复）

> 状态：已完成，测试 0 failed（后端 694 / 前端 178 全量通过）
> 关联：`changes/plan-creation/技术方案.md` §5.1/§5.2、`services/chat/src/plan/schedule-builder.ts` R3

## 1. 背景与问题（用户反馈，已核实属实）

创建计划页（`/plans/new`）填写：目标 100 USD、计入已有外币 40、均衡节奏。

| 反馈现象 | 复现结论 |
| --- | --- |
| 排期预览显示 33.33 / 33.33 / 33.34（合计 100），切换节奏重算后仍如此 | 属实：预览按**全额目标**排期，未扣减计入的 40；真实落库应为 60 的三等分（20/20/20） |
| 计入 100 时，安心型仍显示 50 / 30 / 20 | 属实且更严重：预览给出排期，但该参数下创建时分批总额 = 100 − 100 = 0，后端必抛 `AMOUNT_TOO_SMALL`（400），预览给出的是**创建必失败的虚假承诺** |

## 2. 根因

「计入已有外币」（`allocatedAmount`）没有接入排期预览链路，扣减只发生在创建时，三层断点：

| 层 | 位置（修复前） | 问题 |
| --- | --- | --- |
| 后端 service | `services/chat/src/plan/plan.service.ts` `preview()` | 硬编码 `allocatedAmount: new Prisma.Decimal(0)` |
| 后端 DTO | `services/chat/src/plan/dto/plan.dto.ts` | `SchedulePreviewDto` 无 `allocatedAmount` 字段（仅子类 `CreatePlanDto` 有） |
| 前端 hook | `clients/chat-web/lib/hooks/use-schedule-preview.ts` | `SchedulePreviewInput` 不含该字段，预览请求从不携带 |

排期公式（schedule-builder R3）：`分批总额 = 目标 − 已使用 − allocatedAmount`，预览时第三项恒 0。

设计溯源：实现忠实于原技术方案 §5.1（预览请求体仅 5 字段），缺陷在设计层——预览不反映扣减，导致预览与落库排期不一致。

## 3. 方案

预览与创建同口径：`allocatedAmount` 上移至 `SchedulePreviewDto`（可选，缺省 `"0"` 行为不变），`preview()` 与 `create()` 共用同一解析与扣减逻辑。

- **职责分层保持不变**：预览不做余额 409 拦截（caps 随响应返回由前端体验层预检，create 事务内权威重检）。
- **前端本地预判**：`计入已有外币 ≥ 目标金额` 时不发请求，直接提示「无需分批准备」（该状态下创建必被后端拒绝，不展示误导性排期）；`AMOUNT_TOO_SMALL` 错误文案同步更新为覆盖「计入过多」场景。
- **向后兼容**：`allocatedAmount` 可选；缺省/`"0"` 时排期与修复前逐位一致（接口测试 #3b 锚定）。

## 6. 影响范围与风险

- **不变**：创建/落库逻辑零改动；`SchedulePreviewDto` 加可选字段向后兼容；E2E `T-PLAN-001`（填计入 5000 < 目标 10000）不受影响。
- **行为变化**：创建页预览排期从「全额目标」变为「目标 − 计入」——即本次修复目标；计入 ≥ 目标时预览不再展示排期，改为提示文案，且创建按钮禁用（与后端拒绝一致）。
