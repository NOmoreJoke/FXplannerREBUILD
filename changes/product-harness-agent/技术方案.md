## 1. 架构总览与模块边界

1. **独立 `ProposalModule`（`services/chat/src/proposal/`）**：
   - 在 `services/chat/src/app.module.ts` 唯一注册，并纳入 `scripts/check-org-scope.ts` 的 `TARGET_MODULES` 与 `TENANT_MODELS`。
   - 负责 `AgentProposal` 8 态状态机、参数微调重算、`LedgerRevision` 乐观锁比对、人工持锁确认入账（调用 `PlanService`、`TransactionService`、`UsageService`、`CorrectionService`）及待确认角标统计 `GET /api/organizations/current/proposals/summary`。
   - **解耦原则**：`services/chat/src/ai/` 仅调用各领域只读 `preview` 并写入 `PENDING` 提案，绝不直接依赖业务写入方法。
2. **知禾多子图编排（`services/chat/src/ai/agents/`）**：
   - 基于 LangGraph `StateGraph` 构建：`PreDispatchPermissionGate` → `IntentRouter / SupervisorPlanner`（显式 `intent` 0 跳直派，自由对话最多串联/并行 2 个专员子图）→ 4 个专员子图注册表（`market` / `ledger` / `plan` / `explainer`，工具全经 `services/chat/src/ai/tools/tool-guard.ts` 闭包鉴权）→ `DeterministicRuleEngine`（每次必跑）→ 可选 `ComplianceReviewerAgent`（落库解读必跑，按 `snapshotHash` 缓存）→ `ZhiheSynthesizer`（唯一对外第一人称发言者，输出槽位绑定帧）。
3. **同源合规词库（`services/chat/src/ai/compliance/compliance-lexicon.ts`）**：
   - 供后端运行时规则校验器与静态 CI 门禁 `scripts/check-compliance-copy.ts` 共读，杜绝词表双写漂移。
4. **前端双模翻转与存折检视台（`clients/chat-web/components/business/collab/`）**：
   - 以 URL（`/chat?ctx=<type>:<id>&intent=<intent>&return=<safePath>`）为唯一状态来源，复用 `clients/chat-web/lib/auth/safe-redirect-path.ts`。
   - 通过 `memberCount === 1` vs `> 1` 驱动 `Solo-First / Team-on-Demand` 文案与协作元数据渐进显露。

## 2. 数据库 Schema 与 `LedgerRevision` 触发器设计

### 2.1 新增表与列（Stage 1 `W40` 迁移）
1. **`ledger_revisions`（`LedgerRevision`）**：
   - 主键 `(organization_id, currency_code)`，`revision BIGINT NOT NULL DEFAULT 1`；外键关联 `organizations(id) ON DELETE CASCADE`。
   - **单调不重置铁律**：`services/chat/src/data-request/data-request-cleanup.ts` 执行账本 `CLEAR` 时严禁删除该表行，清空删除各账本表行的动作自身会触发修订号继续递增。
   - **数据库触发器覆盖清单（对照 `services/chat/prisma/schema.prisma`）**：
     - 在 `accounts`、`transactions`、`initial_holdings`、`cost_lots`、`usage_records` 5 张主表建 `AFTER INSERT OR UPDATE OR DELETE` 语句级触发器，按 `(organization_id, currency_code)` upsert `revision = revision + 1`；
     - 在 `plans` 表建 `AFTER INSERT OR UPDATE OR DELETE` 触发器，按 `(organization_id, target_currency)` upsert `revision = revision + 1`；
     - 在 `plan_allocations` 子表建 `AFTER INSERT OR UPDATE` 触发器，通过 `plan_id` 关联 `plans` 取 `(organization_id, target_currency)` 补增。
2. **`agent_proposals`（`AgentProposal`）**：
   - 字段：`id, organization_id, conversation_id, message_id, agent_run_id, created_by_id, confirmed_by_id, kind, status, invalid_reason, supersede_key, input_payload(JSONB), preview_snapshot(JSONB), base_revisions(JSONB), target_version, quote_at, expires_at, committed_target_type, committed_target_id, created_at, resolved_at`。
   - 状态枚举：`PENDING | STALE | CONFIRMED | DISMISSED | EXPIRED | SUPERSEDED | INVALIDATED | LEGACY`。
   - 容器默认有效期 `expires_at = created_at + 24h`（`config/` zod 校验）；`TX_BUY` 若依赖实时参考价折算，报价时效直接复用 `services/chat/src/rate/rate.constants.ts:87` 的 `QUOTE_TTL_MS`（5 分钟）；每人每组织 `PENDING + STALE` 上限 20 条。
   - 存量迁移：将现有 `ai_messages.plan_draft IS NOT NULL` 行幂等回填为 `status='LEGACY'` 只读提案。
3. **`ai_messages.resolved_slots JSONB`**：
   - 消息落库时一并冻结每个 `{{slotKey}}` 的 `{ value, display, unit, source, asOf, baseRevision }`，历史回看只读该列。

### 2.2 确认入账比对与错误码收敛
- 持 `lockOrganizationForActor` 锁重读最新成员资格、角色与 `ledger_revisions`：
  - 修订号未变且实时报价未超 `QUOTE_TTL_MS`：同事务执行业务写入 + 更新 `agent_proposals(CONFIRMED)` + 写 `AuditLog(actorType="USER", detail={ proposalId, agentRunId, userEdited, fieldDiff })`。
  - 修订号已变：服务端自动重跑对应只读 `preview`——若关键输出完全一致则刷新 `baseRevisions` 直接放行（返回中性提示标记）；若有差异则返回 `409 PROPOSAL_STALE { reason: "LEDGER_DRIFT" | "TARGET_CHANGED" | "QUOTE_EXPIRED", diff }`（兼容映射原 `CORRECTION_TARGET_CHANGED`，并登记进前端 `isExpectedControlFlowApiError`）。
  - 遇个人/组织双锁：原样返回 `403 ACCOUNT_PENDING_DELETION / ORGANIZATION_DATA_LOCKED`，不改写提案状态，交由前端 `consumeDataRequestLock` 跳转 `/data-requests`。
