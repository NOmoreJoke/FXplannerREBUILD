## 2. 接口契约（增量，全部需登录）

统一响应包装 `{ success, data, message }`；错误体统一 `{ code, message }`。

| 功能入口 | 方法与路径 | 语义 |
| --- | --- | --- |
| 完成态判定 | `GET /api/onboarding/status` | `{ completed, requiredConsentsMet, settings: { baseCurrency, … } \| null, currentTermsVersion }`；前端据此跳过向导 |
| 条款确认 | `POST /api/onboarding/consents` | 记录 `age18` 与 `terms` 两条确认（当前版本），重复确认幂等不报错 |
| 完成设置 | `POST /api/onboarding/complete` | 事务内：① 校验年龄+当前版本条款已确认（`400 CONSENT_REQUIRED`）② 校验本位币 15 币种之一 ③ 已有设置 → `409 ONBOARDING_ALREADY_COMPLETED`（本位币锁定）④ 创建 `UserSettings`（baseCurrency + 偏好，`ledgerStartedAt = 完成时刻`）。请求体即完整最终数据（region/locale/baseCurrency/prepPreference/reminderEnabled） |

向导中间内容不做后端存储：向导各步数据仅存前端本地内存，未点完成即退出则全部丢弃、下次从头重填（需求文档 §一.2.8）。

本位币锁定的保证：`UserSettings` 创建后，全代码库不存在更新 `baseCurrency` 的写路径（本模块无更新入口；M11 清空业务数据时按 M0 方案保留 baseCurrency）。

## 3. 关键实施细节（并发、竞态、边界）

### 3.1 complete 的原子性与并发兜底

- `POST /complete` 全程在 `prisma.$transaction`（交互式事务）内：校验条款 → 创建 UserSettings，任一步失败整体回滚。
- 并发/重复提交的最终防线是 **`UserSettings.userId` 唯一约束**：两个并发 complete 同时通过“是否已有设置”检查时，第二个在插入处触发 P2002，映射为 `409 ONBOARDING_ALREADY_COMPLETED`。不依赖“先查后建”（存在 check-then-act 竞态窗口）。
- `ledgerStartedAt` 取事务内同一 `new Date()`，保证“记账起点 = 确认成功时刻”（doc 01）。

### 3.2 条款确认幂等

- `POST /consents` 对 `(userId, termsVersion, consentType)` upsert（M0 唯一约束兜底）：重复确认不报错、`consentedAt` 保留首次时间不覆盖。
- “当前必要条款”判定：存在当前 `CURRENT_TERMS_VERSION` 的 age18 与 terms 两条记录。termsVersion 为模块内常量（当前唯一版本），本期无新版条款流程。

### 3.3 OTP 锁定的竞态容差

- 15 分钟输错计数为“查询窗口内 sum 后判断”，两个并发验证请求同时失败时可能都读到 4 → 都不触发锁定（实际累计 5）。该竞态容忍：OTP 锁定是防滥用限流而非资金安全控制，差 1 次的窗口影响可接受，不为它引入串行化（防过度设计）。
- IP 维度限流（60 秒 5 次）保留现状，与邮箱维度限流叠加生效。

### 3.4 币种校验来源

- baseCurrency 合法性用 money 包 `CURRENCIES`（15 币种）校验，与 rate 模块同源；`GET /api/currencies`（DB 表）仅用于前端展示，不做校验依据。

## 5. OTP 补全的语义设计（不新增字段）

- **10 分钟有效期**：`OTP_EXPIRY_MS` 5min → 10min（单点常量）。
- **1h/24h 发送上限**：发送前按目标邮箱统计近 1h/24h 已成功创建的验证码条数，≥5 / ≥20 → `429 OTP_SEND_RATE_LIMITED`（提示对应等待语义）。纯查询现有记录即可，不加字段。
- **15 分钟输错锁定**：验证失败时按邮箱聚合近 15min 内所有验证码的累计尝试次数（含本次），≥5 → ① 该邮箱全部未消费验证码立即作废 ② 返回 `429 OTP_VERIFY_LOCKED`。此后验证与发送入口先检查锁定期（15min 内累计 ≥5 即视为锁定），期满自动解除。不加字段，由现有记录推导。

- **需求文档**：删除「设置草稿」条款（原 §一.2.6）与术语表行；验收标准删原 5/6，「条款先行」不再涉及草稿；新增「向导中断重填」验收标准。
- **本方案**：删除草稿接口（PUT/GET/DELETE `/api/onboarding/draft`）与 `GET /status` 的 `draft` 字段（§2）、§3.2 草稿惰性删除设计、§8 全部草稿用例。
- **实现**：schema 移除 `OnboardingDraft` 模型，迁移 `20260914055601_remove_onboarding_draft`（drop table，含外键）；删除草稿 API/DTO（`SaveDraftDto`/`OnboardingDraftMetaDto`/`OnboardingDraftContentDto`）/异常（`DRAFT_NOT_FOUND`/`DRAFT_EXPIRED`）/常量（`DRAFT_TTL_MS`）；`POST /complete` 事务内不再删草稿。
- **契约**：重新执行 `bun run generate:api`，公开操作数 19 → 16。
