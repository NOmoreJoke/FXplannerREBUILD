# 第一阶段 Agent：范围、职责与入口

状态：已形成配置与接口设计，尚未实现。用户授权范围为设计与配置，不写运行代码。

## 1. 第一阶段要解决的问题

用户已有目标、持仓、交易和计划分配数据，希望得到一份说明当前持仓成本、还需准备多少、固定分批方案及参考比较的报告。

目标是可靠地解释、推荐服务生成的合法方案。现阶段不让模型决定金融数值，不采集当前本金余额，不执行交易，不自动记录或分配资产。

核心输出：

- 目标和数据时点摘要。
- 按来源成本币分列的持仓和成本；初始折算与真实取得成本区分。
- 目标历史有效使用、当前计划剩余分配及缺口。
- 固定候选、服务选择的推荐及其理由。
- 已配置、质量合格时的期限盘面参考比较；缺失时保留其他内容。
- 已有确认安排与执行事实；无法匹配的执行不猜测。
- 数据局限和明确的下一步入口。

## 2. 首发与未来能力

| 能力 | 第一阶段 | 后续预留 |
|---|---|---|
| 三批固定比例 | 开启；两批/一批按既有日期规则 | 可变批数、用户自定义 |
| 比例基数 | 当前计划版本的初始缺口 | 每次剩余缺口；需要独立续排规则 |
| 准备偏好 | 已确认前置/均衡/后置；未选时均衡 | 多维偏好、受限市场信号调整 |
| 行情 | 读取工程化服务提供的可信结果 | 新供应商、曲线方法与经过验证的信号 |
| 期货曲线 | 参考解释，质量合格才比较 | 不自动取得预测或择时权限 |
| 执行回填 | 读取现有账本和分配的新事实 | 新增贡献映射及滚动重排 |
| 部分执行后的候选 | 不新生成重排候选；解释原安排和最新事实 | 规则确认后的续排 |
| 短中长期 | 不启用未确认阈值 | 版本化产品参数，不用论文代替参数验证 |
| 自由对话 | 默认关闭 | 绑定报告的只读追问 |
| 报告类型 | PLANNING、PROGRESS | 按独立能力启用其他类型 |

已确认安排的金额与当前缺口可以因执行而不相等：原安排是历史事实，不能强制改到与新缺口一致。只有新候选金额合计才必须等于其生成快照的缺口。

## 3. 五个角色不等于五次模型调用

| 角色 | 第一阶段执行模式 | 输入与交付 |
|---|---|---|
| 主 Agent | 受控工作流与确定性路由 | 已鉴权请求→报告任务；自由意图识别提示词仅预留 |
| 数据 subagent | 只读工具，不需要LLM | 资源引用→冻结快照、来源与完整性状态 |
| 策略 subagent | 规则选择与固定理由，不需要LLM | 合法候选→确认的候选ID和理由；策略说明契约供扩展 |
| 报告 subagent | 模型；失败可用固定事实模板 | ProviderInput→ModelOutput |
| 审计 subagent | 程序检查＋独立模型语义检查 | 原始可信快照、报告草稿及哈希→通过或拒绝 |

完整提示词仍交付五个角色，便于后续平台接入。当前不激活的模型模式不能在界面上被描述为“已由多个AI共同判断”。角色是责任边界，实际调用模式由配置决定。

撰写与审计可以使用同一型号，但必须使用独立调用上下文。审计没有撰写者的推理过程和自我评价，直接看可信输入与待审草稿。两个模型认可不代替程序校验。

## 4. 确定性计算和策略选择

业务服务计算 G=max(T−U−A,0)。T为目标原始总额，U为该目标全部历史计划有效累计使用，A为当前进行中计划剩余分配。

数据服务负责账本及成本；准备服务负责合法日期和候选；比较服务负责基准、行情和费用口径。数据 subagent不拼写SQL、不执行任意查询、不接触数据库凭据，也不把模型生成的数据提升为账本事实。

三批采用前置50/30/20、均衡三等分、后置20/30/50；两日采用60/40、50/50、40/60；一日100%。首/中/尾日期、币种精度及尾差按已配置MVP规则计算。无日历不可生成新安排；无合法日期不可生成正常候选。已有有效安排可继续展示，并说明时效。

选择顺序：

1. 先检查生命周期和候选合法性；终态不进入新生成入口。
2. 服务端核验执行状态：只有草稿，或相对于当前确认安排基线已核实尚未开始的计划，才可进入新候选生成；状态未知或已开始时只展示原安排与当前事实，selection为空，分别记录 EXECUTION_STATUS_UNKNOWN 或 PARTIAL_EXECUTION_REPLAN_DISABLED。不存在执行匹配不能证明尚未执行。
3. 准备缺口为零：不提供新增购汇候选；备齐不等于实际使用或完成。
4. 用户已有明确的结构化准备节奏，选择对应合法候选。
5. 未明确节奏，使用均衡合法候选。
6. 对应节奏无合法候选时不偷偷换一种，保留无候选及原因；通过既有预览入口处理。

自然语言“激进一点”“等便宜了再买”不能直接改变确认偏好；主入口引导到结构化设置。阶段A不启用单凭用户自由文字触发 USER_REQUESTED_EARLIER_PREPARATION 的选择分支。

## 5. 编排步骤与失败处理

1. 网关检查JWT、对象归属、资源版本、幂等键、报告类型与生命周期。
2. 数据工具在一致读取边界内组装可信快照。对账户、分配、使用与成本进行领域校验。
3. 服务核验ExecutionGate，按允许范围生成候选并完成规则选择；校验完成后的 ProviderInput 投影脱敏、冻结并计算 context_hash，执行门控与同一snapshot_id一起不可变保存。
4. 报告模型只收到白名单ProviderInput及固定system；不接收真实用户ID、银行卡、凭据或完整备注。
5. 对模型输出执行JSON、Schema、ID、指标占位符、候选、状态、范围和事实一致性检查。
6. 通过程序检查后，独立审计模型读取该快照、草稿及草稿哈希。输出接受或拒绝及具体问题。
7. 模型故障、草稿不合格或语义审计拒绝/不可用：丢弃AI草稿，使用固定事实模板，再完成程序输出校验。不得把语义审计失败写成通过。
8. 原始业务快照严重冲突：直接拒绝，不用模板掩盖。
9. 报告、外层审计摘要和幂等完成状态成功持久化后才返回 generated。存储失败返回 retryable_error；同键恢复已冻结结果，不重复生成。

模板必须由预先审查的固定表达组成，不能把被拒绝的AI句子塞回模板。模板送达时，质量说明表示“规则核验通过”，不能显示“AI语义审计通过”。

同一请求下的模型调用总上限建议三次：撰写最多两次（一次结构修复），独立审计最多一次；总模型时间预算建议三十秒，均为待实测起始参数，不是性能承诺。只有JSON/Schema/长度问题允许结构修复；金融事实、越权、预测承诺错误直接回退。

旧GenerationMeta.attempts只记录撰写角色的调用次数，保持其单模型语义；新增pipeline_audit记录跨角色总数及各角色次数。业务输入状态READY/DEGRADED与模型是否可用分别记录。

## 6. 数据与DDD边界

本包定义一个“报告编排”应用服务，不建立新账本。目标、账户/成本、分配/使用、排期、行情比较、报告快照保持各自责任：

- 上游业务服务提供授权、版本化的只读快照或Repository适配。
- 报告编排只保存报告、生成状态与审计，不修改目标、余额、交易、分配或正式安排。
- 用户确认修改沿用原业务服务和权限检查；模型只能给出允许的页面入口。
- 领域变化使旧报告标记为事实已更新；旧报告不改写，用户可重新生成新快照。
- 不为此MVP引入新的CQRS或事件溯源平台；审计记录与不可变报告快照不等于全系统Event Sourcing。

真实数据库适配尚未实现。本文中的可信快照来自工程化服务这一前提，需要开发验证，不能用客户端上传的账本JSON替代。

## 7. Chatbot入口建议

首发主入口：计划详情→生成规划报告。用户可以选择关注持仓、分批、参考比较等主题，不需要通过闲聊逐个提供已有数据。

报告更新入口：已有报告→提示事实已更新→重新生成。重生报告不等于更新正式计划。

可选未来入口：“问问这份报告”侧栏，问题例如“为什么推荐这个节奏”“已有持仓成本怎么算”“这项参考差额为什么不可用”。回答绑定 report_id和snapshot_id，并显示依据时点。

不把Chatbot作为首发唯一入口，理由是目标/金额/日期已有结构化表单，报告流程固定，聊天会额外引入意图歧义、会话状态和修改确认链路。适合下一阶段先做只读追问，再评估自然语言建计划。

未来对话不直接访问实时账本或重新取价；用户请求最新结果时进入“重新生成”。修改目标、回填交易、分配和策略转到明确的业务确认页面。发送回答也须完成指标、来源与语义校验后再展示，不流式展示未审查的金融结论。
