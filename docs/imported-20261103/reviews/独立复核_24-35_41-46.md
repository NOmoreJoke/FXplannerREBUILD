## 24：S02 报价失败分支

**证据。** [02:41–45](../../MVP功能模块&业务逻辑&专业术语/02_初始化与录入闭环_待确认.md#哪些报价可以使用) 规定失败显示原因、保留草稿、禁止无效替代价；明确“允许重试”在 05:32。16:80–91 只有返回报价后核对及“报价过期或依据变化”，没有查询失败分支。16:97 已有失败不以 0 或手填价替代，故不是模型完全放开失败入账。

**最小修订。** 在 S02 查询报价后增失败/无有效报价分支：返回来源最后时间与原因，保留草稿，允许重新查询，不进入可确认状态；成功才展示全部核对报价。引用 02:39–47、05:30–32。

**业务决策。** 无新增决策；不要另造失败可手填政策。

## 25：起点同日补录确认

**证据。** 02:88–91 明确起点同一天买入/使用须额外确认“发生在记账起点之后，且未包含在初始金额中”。S03 的 16:111–131 与 S06 的 16:208–227 只有一般核对和资金检查，没有此额外用户确认。通用检查 16:31 不能代替可见的防重复入账确认。

**最小修订。** S03、S06 在预览阶段增加仅适用于记账起点同日补录的确认；提交时检查该确认仍对应当前日期/金额/起点。更早日期禁止、未来日期禁止均引用 02:88–90。

**业务决策。** 无；按已定规则补模型。不要把每笔当日记录都强制额外确认，触发条件是“与记账起点同日”。

## 26：更正重试与幂等

**支持。** 02:133 规定结果不明先查原请求、确认失败后可重试。18:143 将明确 REJECTED 列作终止，18:153–160 图没有已确认失败后的再次尝试路径，也没有说明重试是否作为新操作开始。

**反证。** 18:179 已明确初始更正结果不明先查询原请求、不再次创建；18:168 排除了把未知结果当明确失败。16:32 有通用幂等/未知结果口径。17:113 E24 虽未名为“幂等键”，已有“更正身份”；17:3 明说是逻辑模型，不承诺 API 或物理表，因此“没有专用字段”不能直接证明冲突或缺少防重能力。

**最小修订。** 补初始更正专属“正在确认结果”与查询原操作路径；明确失败后可从同笔更正重新核对并重试。说明请求/更正身份如何关联原结果和后续尝试，保留失败历史。若 REJECTED 保持不可变终态，明确“重试创建新尝试并关联原尝试”，无需强行把失败事实改回编辑中。

**业务决策。** 已确认失败可重试，不需再问是否允许。请求标识及尝试身份属于实现设计。普通买入/使用超时细则仍待定，不能借此统一放开自动重试。

## 27：未来报价

**支持。** 18:75 的“来源/方向/时间齐全、正值、未满5分钟”与 17:98 的“不足5分钟”都未显式写 `报价时间 <= 核对/提交时间`；若独立翻译成只检查 `age < 300`，负年龄会漏过。

**反证。** 02:42 明确时间在未来不能采用，16:97 也包括时间检查；17:98、18:55 关联 02。本次只审文档，不能说真实系统已经接受未来报价。

**最小修订。** 将初始核对/提交守卫完整写成 `0 <= 采用时点 - 来源报价时间 < 5分钟`，并继续检查来源、方向和有效正值。历史补充/币种更正用“原确认时刻”作为采用时点（02:122），已入账快照不按今天重新过期。

**业务决策。** 无；不自行加入容忍未来时钟偏差。

## 28：初始更正报价条件范围

**支持。** 18:167、173 为初始更正笼统写“原时点报价/原时点有效报价”，未区分 02:115 的纯金额更正沿用原采用汇率与 02:117、122 的改币/补币历史查询条件。

**反证。** 这些守卫没有写“所有更正都必须重新向来源查询”；已有原快照本可满足原时点有效性。02:120 另规定仅来源正式更正原报价时才允许替换汇率。因此称模型已经扩大为“每次都需要新查询”证据不足。

**最小修订。** 拆成：金额更正沿用已保存的原采用汇率；币种更正/漏填按原时点有效历史报价；来源正式更正时按可核对依据替换并展示差异。引用 02:115–124。同步澄清 16:362 的压缩表述。

**业务决策。** 无；不能把缺历史数据的币种更正改成手填或今日价。

## 29：资金已备齐／钱已备齐

**证据。** 04:71、14:44 用“资金已备齐”；08:11、15，13:32，15:36 用“钱已备齐”。15:36 与 04:71 指向相同派生条件，不是两个生命周期状态。18:363 列清“剩余需求>0且分配足够”。

**最小修订。** 建议 UI 标签采用“资金已备齐”，15 保留“钱已备齐”为解释性别名，并将它和“资金已使用完成”“已完成”分开。正文自然语言可保留“钱备齐”，不需要机械替换每个说法。

**业务决策。** 仅文案规范选择，无新业务规则；未验证原型标签。

## 30：后继计划／接续计划

## 31：未分配余额／账户可分配余额／可分配余额

**证据。** 04:21 与 06:53 均为账户余额减所有计划剩余分配；04:88 使用“可分配余额”，10:18/28 使用“账户可分配余额”；15:31/63 定义“未分配余额”。

## 32：还需使用指标多名

**证据。** 15:29、14:31 用“还需使用金额”；04:69 用“目标还需金额”；06:28、16:149 用“目标剩余需求”；06:55 又用“计划还需要使用多少”；17:139 给出目标层公式。它们在上述位置指目标总額减全部计划有效使用、最低为0。

**最小修订。** 指标规范名建议“目标还需使用金额”，别名纳入 15；公式固定 `max(目标金额 - 目标累计已使用, 0)`。若优先少改，可沿用已有 15 的“还需使用金额”，在定义中明确目标级。06:34“本计划承接金额”是创建时快照，不应当作持续变化的该指标替换。04/06/08 漏写“当前”的问题归清单13，避免重复计数。

**业务决策。** 名称选择即可，不能顺手更改目标累计使用范围。

## 33：还需准备／资金缺口／计划还缺多少

**证据。** 15:32 与 14:34 定义“还需准备金额”；06:52“计划还缺多少”同公式；14:132/148 等例子用“资金缺口”。17:141 也给出 `max(剩余需求 - 当前计划剩余分配, 0)`。15 全表没有“缺口”条目。

**最小修订。** 规范为“计划还需准备金额”，15 建“资金缺口”别名；简短 UI 可使用“还需准备”。保留已完成更正的“目标差额”概念，不把终态差额改成待补缺口（08:47–51、18:366）。

**业务决策。** 文案统一即可，无新资金规则。

## 34：均价及派生指标定义

**支持。** 15:21–24 收录单位成本、平均成本、使用成本，但没单列使用均价；04:22 与 09:51 的平均单位成本/单位平均成本语序不同；15 没单列账户已分配金额和资金已使用完成。

**反证。** 04:20 已定义账户已分配金额；04:75、14:44、18:363–364 已定义资金已使用完成的提示与计划尚待用户确认完成的关系。11:11–14 也明确使用均价仅单一成本币且资料完整、零使用 N/A，故不是全文无定义。

**最小修订。** 15 补“使用均价＝该计划相应已使用成本／对应已使用数量”的适用条件，按11区分来源币、完整性与 N/A；账户剩余成本的均价另列“账户剩余平均单位成本”。补账户已分配金额等于全部计划剩余分配之和、资金已使用完成的派生条件。不要把使用均价和账户剩余均价当同义词全量合并。

**业务决策。** 已有条件可直接整理。多成本币是否逐组展示使用均价、未知费用时哪些局部均价可显示，应沿用原文范围，若要扩展需单独决定；不能因新增术语擅自开放。

## 41：公共计价币

**证据。** 05:26 使用该词；15:3–57 未收录。05:3/26 已明确只记录 A→B、相除只用于报价计算、不产生中间成交，因此尚不能说正文自相矛盾。

**最小修订。** 15 增技术术语及注明不是持仓或成交步骤。示意即可：若同一来源及可比时点报价为 `1 A = x C`、`1 B = y C`，则 `1 B = (y/x) A`；不应不带方向直接写“相除”。例如 `1 CNY = 0.14 USD`、`1 EUR = 1.08 USD`，则 `1 EUR ≈ 7.71428571 CNY`；这里只做数学示例，不是实时报价。该词一般不必出现在用户操作流里。

**业务决策。** 实际数据源、支持币种及时效仍按05:42–46待定；不在示例中默认采用某供应商。

## 42：配置变化后的初始草稿重核

**原主张不成立。** 01:108 写的是“核对其记录采用的币种”“不静默替换金额单位”，随后立即限定历史交易沿用原币、正常更正沿用原记录规则。02:107/119规定补充沿用原记账起点成本币、初始记录原日期/成本币不改。重新展示/核对交易对并不等于把初始记录改成本次默认币，两段兼容。

**最小修订。** 可在01:108追加例子：“初始持仓补充沿用原记账起点成本币；已有初始记录更正沿用该记录成本币，重核不换币。”无需把提示范围缩到普通买入草稿，否则反而删掉已有的跨配置确认保护。

**业务决策。** 无。

## 43：首页空态、提醒关闭与多成本币

**支持。** 03:32–34 将摘要细节及没有数据/加载中/失败呈现留待确定，03:7/42 也未指定多成本币在首页摘要的具体布局。

**反证。** 空态等已登记为待确定，不是未记录的逻辑矛盾。08:3 已明确关闭主动提醒后页面仍显示日期、缺口、计划进度；04:27–29 和11:7/19 给出成本按来源币分组、不可相加的统一口径，并非首页可以另算总成本。

**最小修订。** 保留待定身份，补首页状态矩阵：无账户/无目标/无计划/无提醒分别展示什么，加载中与失败的局部恢复入口；提醒关闭仍展示状态。首页成本摘要复用04的分币口径，空间不足用分项或“多币种成本”进入详情，不造跨币总额。

**业务决策。** 摘要展示条数、折叠方式、具体空态布局尚需产品/设计确定；现有后台或记录行为无须扩展。

## 44：更正币种自动建立账户

**原主张不成立。** 04:7 的“更正交易币种后……自动建立”描述成功后系统动作；09:26–31 已要求先看影响、确认、成功才保存，09:51 明确先提示新增账户且更正成功才创建。自动建账户不等于跳过用户确认，二者兼容。

**最小修订。** 为减少跨章跳读，可将04:7改为“提示并经用户确认、更正成功后自动建立（见09）”，属于表述对齐，不列为冲突或独立关键缺陷。

**业务决策。** 无。

## 45：16 模块对应索引

**证据。** 16:10 的02行仅 S02/S03/S10、SM03/06，未列其补录使用规则对应 S06、清空新起点对应 SM09；16:13 的05行仅 S03/S10，未列05:28–38覆盖的首次报价 S02；16:15 的07行未列其07:66–68停旧建新安排对应的 S09；16:17 的09行未列它09:7进入的 InitialHolding，17:97却明确将09列为 E08 来源。

**最小修订。** 补上述交叉映射，02若做完整清空对应可同时列 S14/SM09。将表头说明为“主要映射＋关键交叉映射”，并统一标准，避免为了追求所有引用使矩阵失去可读性。

**业务决策。** 无。只归索引覆盖，不得据此说 InitialHolding 或 S09 根本未建模。

## 46：SM03 数值约束
