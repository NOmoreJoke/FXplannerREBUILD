## 前言：项目概述

### 项目一句话定义

面向中国大陆用户的外币支出管理工具——记账 + 汇率信息助手；不触碰支付清算与投资建议，定位于"规划层"的中立信息服务。

### 申报承诺段（标准措辞）

FXplanner 跨币种现金流规划与外汇成本优化工具，已上线 `app.fxplanner.cn`（HTTPS+HSTS，ICP 已于 2026-04-09 备案）。已完成 Sprint 0~13D（截至 2026-04-15 v3.51）、上线 18 项核心能力、257 项自动化测试通过。自然增长版申报主线：2026 累计注册 4,500、2027 ¥8 万营收（付费 563）、2028 ¥26 万营收（付费 1,563），2028 当年净利 **+¥7.26 万**，三年累计 **-¥1.41 万**（接近持平），累计现金需求峰值 **-¥10.31 万（2027 Q3 末）**，2029 Q1 累计现金流回正。三年累计投入 ~25-46 万元（孵化器口径，不含股权融资）；三年累计带动数字技术岗位 9-14 人次（含创始人 + 兼职 / 外包 + 实习，意向规划）；拟累计软著+商标 8-10 件。陆凯铭为唯一经营 / 持股主体；UBC 数学本科 + FRM L2 候选人 + AI 训练师三级。

### 核心问题与解决方案

**核心问题**：中国大陆居民在留学、跨境工作、跨境自由职业、出境消费等场景下，每年人均存在 ¥2,590-6,335 的可避免外汇成本损失（来源：数据基线 v1.2 表 E）。损失的根本原因不是缺资金，而是缺一个"在花钱之前"做**费用情景比较与预算提醒**的工具。

**解决方案**：FXplanner 提供三件能力——

1. 多源银行汇率与信用卡费率聚合；
2. AI 自然语言交易事件录入与置信度标注；
3. 跨币种现金流建模与提醒引擎。

通过 Web 端（已上线）与未来桌面 / 移动端（Tauri 2.0 规划中）覆盖用户全场景。

### 商业模式摘要

- **用户层**：**主线客群——中国大陆留学生 + 留学生家长（双联动）**，留学生 90-105 万 + 家长 1:1-1:2 比例；扩展客群（跨境工作者 / 跨境自由职业 / 高消费出境旅行者，合计 ~570 万活跃池）2028 视主线 LTV/CAC 数据评估再启动；SOM 用户基数约 675 万（商业假设）。
- **价格策略**：月度订阅 ¥19.9 / 月、季度订阅 ¥49.9 / 季、单次报告 ¥5-10 / 份。
- **变现路径**：试用→付费墙 + 报告增值 + 未来 B2B（留学机构 / 跨境财务顾问）合作。
- **合规边界**：信息服务与规划工具，不参与支付 / 清算 / 换汇执行 / 资金托管 / 便利化额度规避；当前已具备 ICP 备案 + 境内云资源 + PIPL 边界。

### 1.2 技术内容与基础原理

#### 1.2.1 总体架构

FXplanner 采用 **前后端分离 + 后端 DDD 六大上下文 + 数据库/缓存分离 + 反向代理 + 容器编排** 的现代化 Web 服务架构，部署于阿里云华东节点的境内环境，遵循数据本地化要求。

#### 1.2.2 系统架构与数据流图

**当前架构（已上线）**：

终端用户 → Web 前端（Vue3 + TypeScript + Vite + Tailwind / Pinia / vue-i18n / ECharts）→ 1Panel OpenResty 反向代理（HTTPS + HSTS / Let's Encrypt） → FastAPI 后端容器（Python 3.11 / JWT + 邮箱 OTP / WebSocket 通知）→ {PostgreSQL 16（Alembic 001→005） + Redis 7（连接超时 1.0/2.0s）} → 外部依赖：GLM 智谱 AI（glm-5-turbo）、k780 汇率聚合（中行 / 建行 / 交行）、银行直连（农行 / 工行 / 招行）、邮件 SMTP（OTP 发送）。

**规划扩展架构（Sprint H1-H3 + 移动端规划，2026 Q3 起）**：

- **Harness AI 编排层**（多 Provider LLM 路由）：当前主用智谱 AI（GLM glm-5-turbo）；**已规划接入阿里通义 Qwen + DeepSeek + 月之暗面 Kimi 作为同等级备选 Provider**；
- **切换 SLA**：Sprint H1 编排层落地后，**目标 ≤ 4 小时内切换至备选 Provider**——**该 SLA 在首次第三方切换演练完成后由"目标"升级为"承诺"**（与 §6.7.4 接管 SLA 三档化思路一致）；
- **当前阶段（Sprint H1 之前）的过渡预案**：GLM 服务中断或长时间不可用时，FXplanner AI 自然语言录入自动 fail-soft 至手动表单录入（已上线，§1.2.5）；功能可用性不依赖单一 LLM Provider；
- **Agent API**（开放给第三方智能体调用）；
- **MCP Server**（Model Context Protocol，Sprint H3 2026 Q4）；
- **前端 Tauri 2.0 桌面 + 移动 + 本地 Whisper 离线 STT**（Sprint H2-H3）。

**单一 LLM Provider 占比红线定义**：单一 Provider 月度生产环境调用量（次数）或月度生产环境调用费用，**任一指标占总量 ≤ 70%**——以两个指标的较高值为准（保守口径）；不含开发环境 / 测试环境 / 评估基准跑分等非生产场景调用。红线触发动作：自动通过 Harness 路由层将剩余 ≥ 30% 流量分配至备选 Provider；超过 70% 持续两个月即触发供应商重新评估。

> 上述两层架构的可视化图示见**附录 A**。

#### 1.2.3 数据流（典型业务场景）

以"用户文字 / 语音录入"为例：

1. 用户输入"我每月给孩子打 1500 美元生活费"；
2. 前端调用 `POST /api/ai/parse {text}`；
3. 后端调用 GLM 自然语言解析，返回结构化结果 + 置信度标签；
4. 后端查询汇率域，stale-while-revalidate 缓存命中或回源银行直连 / k780 降级聚合；
5. 后端写入"待确认订阅"，前端展示"待确认卡片"；
6. 用户确认 / 修改后入库，后端更新额度 / 预算；
7. 若触发阈值（80% / 90% / 100%），后端推送 WebSocket 事件，前端更新渐变环 + Toast。

#### 1.2.4 后端 DDD 六大上下文

```
backend/
├── shared/            共享内核（crypto、依赖注入）
├── identity/          认证与用户（JWT + 邮箱 OTP + 微信 OAuth）
├── subscription/      订阅域（CRUD、状态机、成本链路 A→B→C 最多 3 步）
├── quota/             额度与预算（年度便利化 5 万美元 + 月度预算 + 三档阈值告警）
├── exchange_rate/     汇率域（多源聚合 + 银行牌价 + 信用卡费率）
├── ai_interaction/    AI 交互（LLM 解析 + 置信度标签 + 待确认流）
└── notification/      实时通知（WebSocket + 票据认证 + 5 类事件 + 指数退避重连）
```

#### 1.2.5 关键技术原理

| 模块 | 原理 |
|---|---|
| **多源汇率聚合** | 直连层（农行无认证 / 工行 POST+Referer / 招行 Origin+Referer）+ 聚合降级层（k780 双参数认证 appkey + sign，覆盖中行 / 建行 / 交行）；前端 localStorage stale-while-revalidate（15 min TTL），后端 Redis 缓存 + 并发化请求；首次响应 ~1.7s，二次访问 0ms |
| **AI 自然语言录入** | LLM Provider 通过 OpenAI 兼容协议接入；**当前主 Provider 智谱 GLM glm-5-turbo，已规划备选 Provider 通义 Qwen / DeepSeek / Kimi**（Sprint H1 Harness 编排层落地后启用同等级路由）；结构化字段抽取 → 置信度标签 → 待确认流 → 用户确认入库；**LLM 不可用时自动退回手动表单**（fail-soft）；**单一 Provider 月度生产调用量或费用占比 ≤ 70% 红线**（Sprint H1 后） |
| **跨币种支出建模** | 在 ≤ 3 步货币转换链路（A→B→C）中，对**已知费率**做费用估算；输出"不同支付方式费用差异 X.XX% 提示"，**不构成投资 / 交易建议** |
| **已知费率路径比较** | 将"币种 × 银行牌价 × 信用卡外汇费率"建模为有向加权图，对**用户主动选定的若干候选路径**进行**费用较低路径提示**；仅基于**已公开的费率信息**做确定性比较，不预测汇率走势，不推荐特定换汇渠道（图论方法实现细节详见附录 A） |
| **多源汇率统计聚合** | 对 6 行牌价（农行 / 工行 / 招行直连 + 中行 / 建行 / 交行 k780 聚合）做加权中位数 + IQR 异常值剔除，输出"基准汇率 + 行间偏离度"，用于成本测算的鲁棒性背书 |
| **用户预算分布建模** | 基于 30 / 90 日历史录入的指数加权移动均值 + 月度季节性成分，对年度便利化 5 万美元额度余量与月度预算做前瞻性预估；建模对象为**用户支出节奏**而非汇率走势，严守合规边界 |
| **额度与预算引擎** | 年度购汇额度（5 万美元法规额度）+ 前瞻性预估（已用 / 含下笔 / 预估年底）；月度预算自然语言配置；三档阈值告警（80% 信息 / 90% 警告 / 100% 柜台办理告知） |
| **实时通知** | WebSocket + 票据认证 + WS URL 自动推导 + 严格 fail-closed + 指数退避重连；5 类事件（额度告警 / 预算告警 / 费用差异提示 / 主动提示卡片 / 系统通知） |
| **中立信息层** | 业务边界严格限定为"信息服务与规划工具"；不参与支付、清算、换汇执行、资金托管。**当前零资金触达边界下不涉及支付、清算、外汇经营牌照；商业化收费上线前完成 ICP 经营许可适用性法务评估**（详见 §3.5 / §5.7 R3） |

#### 1.3.4 合规架构作为战略护城河

零资金触达边界并非"绕监管"的妥协，而是 FXplanner 主动选择的产品架构。该架构在三个维度同时构成竞争壁垒：

| 维度 | 战略价值 | 量化对照 |
|---|---|---|
| **资产轻量化** | 免去支付 / 清算牌照、备付金沉淀、KYC / AML 系统建设、跨区域分支机构监管栈，单年合规与资金成本相对执行型同业可低一个量级 | 跨境支付牌照获取与运营年化成本通常千万元级，而 FXplanner 当前合规栈仅 ICP 备案 + HTTPS / HSTS + PIPL 边界（年化 < 2 万元） |
| **跨区域快速扩张** | 港澳台 / 东南亚国际版（已规划 2028 H2）只需信息服务合规与本地化适配，相对执行型工具进入新市场需重新申请支付 / 收单牌照，**进入时滞差距 18-36 个月** | 同期 Wise / Revolut 进入新市场的牌照审批周期普遍在 1-3 年；FXplanner 国际版灰度路径以信息服务 + 数据本地化为主 |
| **生态互补而非红海竞争** | 信息服务层与执行层解耦的边界，使 FXplanner 与 Wise / 银行 App 等执行型工具形成**上下游互补**而非正面竞争；B2B 渠道（留学机构 / 跨境财务顾问 API）天然不存在牌照冲突 | Sprint H2 Agent API 与 B2B 套餐已规划于 2027 H2 - 2028 H1 上线 |

**结论**：合规架构是 FXplanner 在三年规划期内**保持低成本结构 + 高扩张速度**的核心制度性能力，而非被动避险措施。**§1.3.5 用户主动确认型数据资产**作为动态层补充，**随用户主动确认录入的累积逐步形成中立规划数据层**——两者共同构成 FXplanner 三年期内的复合壁垒（结构性 + 累积性，非绝对性）。

#### 1.3.5 用户主动确认型数据资产（动态护城河）

合规架构（§1.3.4）是结构性静态护城河；除此之外，FXplanner 在数据层正在累积一类**动态数据资产**：

| 数据维度 | 数据来源 | 公开 / 银行 App / 第三方是否易得？ | FXplanner 累积路径 |
|---|---|---|---|
| 银行公开牌价 | 银行官网公开 API + k780 聚合 | ✅ 公开 | 数据本身不构成壁垒 |
| 信用卡明面手续费率 | 各发卡行公开条款 | ✅ 公开 | 已纳入费率库，不构成壁垒 |
| **用户主动确认后的真实生效费率与场景标签** | 用户主动录入 + 主动确认的真实账单 | ⚠️ 银行 App 仅展示自家发卡牌价 + 自家通道；第三方聚合数据多为名义费率 | 随用户基数增长，可逐步形成执行型同业不易直接获得的中立规划数据资产 |
| **用户支付节奏分布与家庭场景标签** | 用户授权后的匿名化录入 | ⚠️ 不公开 | 用于 §1.2.5 用户支出节奏建模；构成产品功能改进数据闭环 |

**壁垒形成机制（措辞软化版）**：

> 用户主动确认后的跨行费率、预算节点、家庭场景标签与费用复盘数据，**可逐步形成执行型银行 App 不易直接获得的中立规划数据资产**——并非"无法复制"的绝对壁垒，而是**结构性不易获取的中立信息层**。

- **冷启动期（2026-2027）**：以创始人时间 + 自营内容 + 社群冷启动获得首批用户的真实录入；
- **复利期（2028 起）**：每条用户主动确认的真实费率录入 → 提升对其他用户的费率比较准确度 → 提升留存与口碑 → 拉高新用户主动录入意愿；
- **结构性原因**：执行型工具（银行 App / 跨境支付）以服务自家通道为目标，缺少"中立比较 + 用户主动确认"的产品逻辑；第三方聚合工具缺少"用户主动确认"环节，无法分辨名义费率 vs 真实费率。

> **关键约束**：所有数据必须来源于用户主动录入与主动确认；**FXplanner 不存原始账单 / 流水 / 卡号**；数据库中保留的只是脱敏后的费率事实（币种 + 通道 + 卡组织 + 实测费率），符合 §3.5.6 OCR / 账单导入数据处理原则。

### 3.4 营销计划

#### 3.4.1 目标市场与主要客户

##### 3.4.1.1 留学生 + 家长双联动 → 获客复利机制

留学生 + 家长是 FXplanner 的 **P0 双联动客群**，两者构成互相驱动的获客复利循环：

| 复利机制 | 描述 | 已锁定的支撑数字 |
|---|---|---|
| **强粘性** | 留学生用户从入学到毕业 4-6 年持续使用；家长在子女毕业后转入跨境支付 / 出境游 / 其他子女的留学规划场景，留存生命周期延长 | LTV / CAC 2027 6-20× / 2028 8-23×（§5.4 精算）—— **低现金获客假设下的目标区间，需由 2026 Q4 真实渠道数据验证** |
| **高转介绍率** | 1 个留学生用户与 1-2 个家长用户高度绑定（§1.4.2 / §2.1.2 比例口径）；家长口碑与微信家长群构成**天然零成本传播渠道** | 渠道预算 §3.4.4 自营内容 + 社群冷启动占主导，KOL 仅在 LTV/CAC 验证后小额试投 |
| **付费意愿** | 留学家庭对子女跨境财务规划的支付意愿与教育消费同位（家长决策 + 家长付费），契合中国教育消费的家长主导特征 | ¥19.9 / 月年订阅相当于年节省价值 ¥2,590-6,335 的 3.8%-9.2%，ROI 透明可解释 |

##### 3.4.1.2 单位经济模型（Unit Economics）极致化路径

FXplanner 的获客逻辑**并非规模优先，而是单人 UE 极致化**。LTV/CAC 6-23× 是**低现金获客假设下的目标区间**（高于行业 ≥ 3× 健康线，但需由 2026 Q4 真实渠道数据校准与验证）——这一结构性优势的来源有三层：

1. **CAC 端**：合规架构（§1.3.4 战略护城河）使获客侧无需依赖大额预算买量，自营内容 + 社群冷启动 + 家长口碑构成主获客路径，三年累计市场进入费仅 ¥4-12 万；
2. **LTV 端**：留学生 + 家长双联动客群天然粘性（§3.4.1.1）使留存生命周期延长至 4-6 年；
3. **结构端**：执行型同业（持有牌照的跨境支付 / 多币种钱包）需在牌照成本、备付金沉淀、KYC / AML 运营、强监管合规等环节持续投入，**单位经济模型天然受其重资产结构约束**；FXplanner 的轻资产架构在 UE 公式中即拥有结构性成本优势。

**结论**：在低现金获客假设下，当 LTV/CAC 长期保持在 ≥ 8× 时，项目在 SOM < 1% 占有率下盈利质量目标定位优于以规模买量驱动的重资产同业——SOM < 1% 是质量护栏，不是增长瓶颈。**该目标区间需由 2026 Q4 真实渠道数据验证**。

##### 3.4.1.3 自我造血路径与潜在加速增长

在 §5.4 财务测算下，2028 Q2 起持续单季正现金流、2029 Q1 累计现金流回正——构成项目的**自我造血**能力，与孵化器口径"非股权融资 / 后资助"扶持模式完全契合。**自我造血确认后**，复利机制（强粘性 + 高转介绍率 + 高 LTV/CAC）才是潜在加速增长的真正驱动力——但这一加速路径在本 BP **不作为申报承诺数字**，而是项目自我造血确认后再行评估的潜在路径。

- ❌ 帮助用户规避外汇便利化额度

**因此本项目当前阶段不涉及以下牌照 / 许可证**：支付业务许可证、外汇业务经营许可、银行业 / 证券 / 基金 / 保险类金融牌照、互联网金融信息中介相关备案。**ICP 经营许可适用性**根据《互联网信息服务管理办法》对有偿信息服务的判断要求，将在商业化收费上线前完成专业法务评估（详见 §3.5.5 ICP 三路径决策树与 §5.7 R3）；**PIPL 对金融账户类敏感个人信息的更高要求**通过现有数据存储边界（不存银行卡号 / 身份证 / 真实交易流水 / 任何支付凭证）**系统性降低敏感个人信息处理范围**（最小化处理 + 前置控制：仅处理邮箱 OTP 登录信息与用户主动录入的非敏感交易事件描述，不接触金融账户类敏感数据）。

#### 3.5.5 ICP 经营许可三路径决策树

**决策时点**：商业化收费上线前 ≥ 3 个月触发专业法务评估，评估结果落入以下三路径之一，每条路径都有可执行落地方案：

| 路径 | 触发条件 | 处置动作 | 时间窗 |
|---|---|---|---|
| **路径 A：申办 ICP 经营许可** | 法务评估认定**构成经营性互联网信息服务** + 申办窗口 ≤ 6 个月 | 先申请经营性 ICP 许可，许可批准后才上线收费；商业化时间推迟至许可获批；过渡期持续做免费灰度 + 用户访谈 + 内容输出 | 申办周期通常 3-6 个月 |
| **路径 B：推迟收费 + 替代交付** | 法务评估认定**需要许可但申办窗口 > 6 个月**（或申办存在不确定性） | 网站继续保持免费灰度运行；如有付费需求，**仅通过线下咨询合同、单次报告人工交付或第三方独立服务平台承接**，并由法务确认不构成"网站内有偿信息服务"；不采用"网站跳转第三方支付"作为规避手段——根据《互联网信息服务管理办法》，经营性 ICP 判断核心是是否"通过互联网向上网用户有偿提供信息或服务"，仅靠跳转支付通道不能规避此判断 | 视申办进度滚动调整；过渡期可持续多季度 |
| **路径 C：维持非经营性** | 法务评估认定**不构成经营性互联网信息服务**（如以独立合同的报告 / 咨询 / 线下交付为主，不在网站内直接有偿提供信息服务） | 维持现有非经营性 ICP 备案；商业化通过单次报告（线下交付独立合同）或一对一咨询（独立合同）实现，不在网站直接收费；网站本身保持非经营性免费内容定位 | 不依赖 ICP 经营许可申办 |

> **法律依据**：《互联网信息服务管理办法》（工信部）规定经营性互联网信息服务实行许可制度、非经营性实行备案制度；判断核心为"是否通过互联网向上网用户有偿提供信息或服务"。本三路径基于该判断框架设计，**任一路径都不构成商业化阻塞**。

#### 3.5.6 OCR 账单导入数据处理原则（PIPL 即时性 + 无状态性 + 本地推理优先）

> **状态说明**：OCR 账单导入功能**当前未上线**，列入 Sprint H1-H2 规划。**未来 OCR / 账单导入功能上线前，将采用以下数据处理原则**（架构性预先设计，避免后续重构）：

- **本地推理优先**：OCR 解析**优先采用客户端本地推理**——Tauri 桌面 / 移动客户端使用 Transformers.js 或同等开源轻量 OCR 模型在用户本地设备完成解析；**原始账单图片不离开用户设备**；
- **云端解析为兜底路径**（仅在用户主动选择 + 单独同意后启用）：若用户主动选择云端解析（如设备性能不足），则采用以下严格约束：
  - **即时性**：账单图片仅在请求处理周期内驻留服务端内存，**处理完成后即时从内存销毁，不写入磁盘、不持久化存储**；
  - **无状态性**：OCR 解析结果仅保留**用户主动确认后的结构化字段**（金额 / 币种 / 日期），原始图片与未确认字段**不进入数据库**；
  - **敏感字段隔离**：识别到的银行卡号 / 身份证 / 真实交易流水号等敏感字段，自动脱敏（仅保留尾 4 位 / 不入库），不出现在用户确认界面或后端日志；
  - **加密传输**：用户上传图片全程 HTTPS + HSTS；OCR 处理位于境内阿里云华东节点，符合 PIPL 数据本地化要求；
- **PIPL 单独同意机制**：上线前完成 OCR 隐私协议法律文本——OCR 处理告知 + **独立于注册登录的单独勾选同意**——符合 PIPL 第 13 条对敏感个人信息处理的"单独同意"要求；用户可随时撤回同意，撤回后云端 OCR 通道立即关闭；
- **路径选择记忆**：用户首次使用 OCR 时强制选择"本地优先"或"云端兜底"，选择记忆于本地设备，可随时在 Settings 重置。

- **2027 Q1 末累计注册 + 试用→付费转化率验证** = 退路 B 启动决策点；
- **退路 C 仅作为孵化器尽调环节"我有最后兜底"的证明项，不主动启用**——退路 A + B 在数据上已使现金需求峰值回到自筹基线可承受边界。

> **结论**：保守退守版下项目仍可活下来——靠的是低固定成本结构 + 三段退路按序削减 + 创始人自筹仅作最后兜底；**不形成"原先 8-15 万自筹突然变 22-25 万"的反噬主线**；全程不依赖股权融资。

### 附录 A：系统架构与数据流图说明

**当前架构（已上线）**：

```
终端用户（Web 浏览器）
    ↓ HTTPS
Web 前端（Vue3 + TypeScript + Vite + Tailwind / Pinia / vue-i18n / ECharts）
    ↓
1Panel OpenResty 反向代理（HTTPS+HSTS / Let's Encrypt 自动续期）
    ↓ app.fxplanner.cn ↘ api.fxplanner.cn
FastAPI 后端容器（Python 3.11 / JWT + 邮箱 OTP / WebSocket 通知）
    ↓                          ↘
PostgreSQL 16              Redis 7（缓存 + WebSocket pub/sub）
（Alembic 001→005）         （连接超时 1.0/2.0s）

外部依赖：
- GLM 智谱 AI（glm-5-turbo，OpenAI 兼容协议）：AI 自然语言录入
- k780 汇率聚合（中行 / 建行 / 交行，双参数 appkey + sign）
- 银行直连：农行（无认证）/ 工行（POST+Referer）/ 招行（Origin+Referer）
- 邮件 SMTP：OTP 发送

WebSocket 实时通知：5 类事件 + 票据认证 + 严格 fail-closed + 指数退避重连
```

**典型数据流（用户文字 / 语音录入场景）**：

1. 用户输入"我每月给孩子打 1500 美元生活费" → 前端 `POST /api/ai/parse {text}`；
2. 后端 → GLM 自然语言解析 → 返回结构化结果 + 置信度标签；
3. 后端 → 汇率域查询（stale-while-revalidate 缓存 → 银行直连优先 / k780 降级）；
4. 后端写入"待确认订阅" → 前端展示"待确认卡片"；
5. 用户确认 / 修改后入库 → 后端更新额度 / 预算；
6. 触发阈值（80%/90%/100%）→ 后端推送 WebSocket → 前端更新渐变环 + Toast。

**规划扩展架构（Sprint H1-H3 + 移动端规划，2026 Q3 起）**：在现有后端基础上新增 Harness AI 编排层（多 Provider LLM 路由）+ Agent API（开放给第三方智能体）+ MCP Server；前端侧新增 Tauri 2.0 桌面 / 移动客户端（Windows / macOS / iOS / Android）+ 本地 Whisper 离线 STT。
