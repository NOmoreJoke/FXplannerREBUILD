# Goal · FXplannerREBUILD 全分支对抗审查与逐项修复

## Goal 目标

对 FXplannerREBUILD 的每条现有源码分支新开一个独立审查任务，逐个复核该分支相对可信基线引入的行为。每条确认需要修复的风险单独派发修复任务，在独立修复分支提交。用本地真实自动化证明修复有效，并独立复审修复及其叠加结果。所有必修风险关闭，所需验证通过，且每项修复均有可追溯的分支、提交和测试证据时，才完成 Goal。

## 执行提示词

在 `/Users/kyle/Documents/工作/知爻/FXplannerREBUILD` 执行上面的 Goal。你负责协调、验收和跟进，直至全部完成或遇到必须由用户解除的阻塞。

### 1. 盘点并冻结候选

- 先读工作区 `AGENTS.md`，检查 `git status`、worktree、分支拓扑、上游和当前提交。需要更新远端信息时使用 `git fetch origin`，保留本地分支和工作区内容。对每条分支记录审查基点、候选的完整 SHA、差异范围和所属工作树。检查远端独有的源码分支并补入任务清单，同名远端跟踪分支的本地和远端状态记录在同一任务中。若本地与远端分叉，将两边独有增量分别列为该任务的审查输入，保留各自基点。
- 对未提交候选，在隔离 worktree 捕获 staged、unstaged 和属于待审变更的 untracked 文件，排除本提示词、凭据、本地配置和运行产物。核对源与快照的路径清单及 diff，记录原始 `HEAD`、快照 SHA 和捕获范围。必要时在专用本地快照分支提交一次，只用于冻结输入。保留原工作区文件、暂存区和原分支引用。冻结后若源变化，记录新旧候选并补审增量。
- 正式审查从各自冻结的可信基线读取 `AGENTS.md`、适用的 scoped 指令和 `docs/VERIFY.md` 及门禁。基线较早、缺少后续文档时，使用用户给定的工作区规则和已固定的项目规范版本，记录引用 SHA。各分支自己的规则变动也纳入审查。

### 2. 每条分支开一个新的审查任务

- 使用独立 Codex 聊天，每条分支一条。审查任务只读，先独立通读该分支增量、需求与调用链，沿失败、并发、重复提交、存量数据和跨模块副作用寻找反例。通过现有测试和边界夹具确认行为，保留最短可复现步骤。初审完成后再与历史结论对账。历史通过记录不抵消新发现，历史问题也必须与当前快照核对。
- 以改动位置、根因和修复方式去重。能定位到上游分支的缺陷由首次引入它的分支负责，下游只记录依赖及复验。每条风险写明编号、严重度、位置、触发场景、预期与实际、证据、适用规则和验收用例。使用 `[Important]`、`[Nit]`、`[Pre-existing]`。独立确认的 `[Important]` 都进入修复。有可复核行为影响的 `[Nit]` 同样单独派修。纯风格建议保留说明。`[Pre-existing]` 归到已纳入审查的引入分支，范围外问题列入待办。
- 首轮审查可并行。每轮后在协调任务更新分支、候选 SHA、审查聊天、风险编号、责任分支、修复聊天、测试结果和状态。后续独立复审使用前序问题记录和本轮增量。发现新问题时单独登记并继续闭环。

### 3. 每条风险单独修复、验证、提交

- 每条待修风险开独立修复聊天及独立 worktree，创建 `codex/review-fix/<分支简称>/<风险编号>`。默认从冻结候选起步。存在依赖或修改同一片代码时，按依赖顺序从已验证的前置修复提交分支，并明确记录父 SHA。独立问题可并行，通过任务隔离避免争写同一文件或测试数据库。
- 一条风险对应一个聚焦提交，含必要的回归断言。优先让回归在未修候选失败、修复后通过。修复任务完成本地实测后，交给未参与实现的人或 agent 复审改动和证据，通过后按仓库提交规范提交。提交尾部附 `Verified: <实际检查>`，遵守 Changesets 与门禁约定。记录验证时的提交或 Tree SHA，核对最终提交内容与受测内容一致。Hook 若改变代码，针对改变的部分补跑。
- 同一失败最多连续自愈三轮。达到上限时保留现场、原始报错、已尝试改动和剩余影响，由协调任务汇报具体阻塞并推进其他分支。依规处置已确认的 flaky 测试，保留未满足的验收项。禁止用删业务断言、`skip`、硬编码 `sleep` 或盲目放大 timeout 取得通过。
- 原分支作为证据保留。修复提交保存在各自本地分支，默认交付本地分支名与 SHA。推送、开 PR、合入原分支或 `dev`/`main` 以及部署需要另行授权。

### 4. 实跑本地自动化，验证叠加后的候选

- 先跑可信基线规定的 `bun run typecheck`、`bun run lint` 和受影响的单元、属性测试。通过后再跑真实 API、集成和 Playwright。按候选版本核对 `scripts/test.ts` 的可用套件，检查 `unit api integration infra web scripts`，涉及精度或测试入口时再实跑 `money`、`dev-log` 对应套件。应执行的项目没有有效测试入口时，按仓库规范补上或记录阻塞。重构用旧实现或黄金样本做差分，精度、幂等、守恒用独立属性测试。测试明细包含命令、退出码、通过/失败/跳过数和证据位置。
- 后端状态流用本地 PostgreSQL 测试库及真实服务代码，验证状态、行版本、金额、分配与留痕。并发用例必须证明两条路径实际竞争并验证精确终态，失败回滚用例核对核心业务行。迁移工具仅在隔离的本地副本或受控夹具上运行，完成盘点、转换、重跑零更新、回滚和保护行对账。线上数据覆盖与外部供应商可用性只按实际证据报告。
- Playwright 连接人类已启动的对应候选前后端，先核对服务工作树、候选与测试端口，再用 `bunx playwright test <相关 spec> --reporter=line`，或候选定义的 `bun run test e2e`。AI 遵守起服禁令。前后端或测试库还未就绪时，先完成可执行任务，再向用户一次性交代待运行的候选、端口与命令。需要 E2E 的分支保持待真实验证，服务就绪后由协调任务继续跑完。
- 用 `codex/review-verified/<分支简称>` 组合该分支通过复审的修复。按拓扑顺序纳入相关上游修复，再纳入本分支修复，避免把历史提交重复带入。用 `cherry-pick -x` 或等价的可追溯方式组合。出现冲突时保留对照并验证解决后的行为。每个组合候选补跑命中的回归和必要的本地自动化，最后对堆叠末端做跨分支回归。本分支与上游均无适用修复时，用冻结 SHA 验收。
